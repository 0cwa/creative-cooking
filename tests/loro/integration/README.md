# Isolated browser RTC integration

This harness joins two isolated browser profiles through the actual T2 RTC frame adapter. Each profile has its own IndexedDB database, Loro peer, signing identity and preaccepted authority record. Test keys are public and deterministic; this is not product pairing. The candidate codec and authority remain experimental.

From a checkout with its pinned dependencies installed, bundle with esbuild 0.25.12 into a task-owned scratch directory:

```sh
agent-heavy -- esbuild tests/loro/integration/browser-client.mjs --bundle --format=esm --platform=browser --outfile="$LORO_SCRATCH/bundle.js"
agent-heavy -- env LORO_TEST_IP="$LOCAL_IPV4" node tests/loro/integration/scenario.mjs "$LORO_SCRATCH/bundle.js" "$LORO_SCRATCH/rtc-transcript.json"
```

The server prints two URLs. Open them in separate, invisible T3 preview profiles. Use a checked local IPv4 address for `LOCAL_IPV4`. The test has no STUN/TURN servers. It substitutes that address for mDNS names in the final SDP, then signs and verifies those final descriptions with the two preaccepted test identities. This same-host substitution is a test limitation, not product signaling or pairing.

The script asserts an injected local failure and import failure, authority denial, signed stored and applied receipts at their durable boundaries, offline recipe and independent purchase edits, out-of-order delivery, duplicate chunks before and after a reconnect, convergence, reopen and exact retry. It verifies both test identity signatures over the final transcript, which includes source hashes, base commit, browser user agents and network conditions. It closes both databases and deletes the fixture databases on success. Close the two preview tabs after the script exits. The RTC scenario runs the file encoding/decoding path in memory; the separate file proof below exercises disk download and upload. It proves neither native interoperability nor global E1 acceptance.

For the encrypted runtime file proof, serve a `file.html` containing `<script type="module" src="/bundle.js"></script>` beside the same bundle. Connect Playwright to a task-owned invisible Chromium-compatible browser and run:

```sh
agent-heavy -- env LORO_SCRATCH="$LORO_SCRATCH" LORO_CDP="$LORO_CDP" LORO_ORIGIN="$LORO_ORIGIN" node tests/loro/integration/file-proof.cjs
```

The browser saves the downloaded encrypted object to `runtime-object.bundle`; the second isolated context uploads that path through a file input. The proof checks authenticated import, exact retry, convergence and IndexedDB reopen. Remove the task-owned download and profile afterward. This test uses preaccepted deterministic test identities, not product pairing or human identity.

## Routed browser direct exchange

`tests/loro-direct.spec.mjs` runs the exported app. It creates two local browser identities, completes the existing household admission and encrypted household file handoff, and opens the same selected household on both devices. The browsers save different cooking edits offline. They then exchange a signed WebRTC offer by file and a signed answer by text. The test compares the two displayed codes and enters them separately. It verifies that both channels can already be open while cooking exchange stays locked until the second confirmation.

The test rejects a different household, an altered SDP, an answer for a different session, and a wrong verification code. It checks the receiving IndexedDB for zero staged or applied updates before confirmation. It observes the actual ICE candidate pair and checks that the full remote SDP, including its host candidates, arrived unchanged at `setRemoteDescription` and remains the current remote description. A failed local save and an injected import transaction rollback each leave a single staged update and no applied record. The sender sees one stored receipt until retry commits the update and adds an applied receipt. A subsequent send skips that applied object. Both browser profiles display all edits after reopening the app.

Build using `agent-heavy -- env EXPO_PUBLIC_BASE_URL=/creative-cooking npm run build:web`. Run the case using `agent-heavy -- npm run test:e2e -- tests/loro-direct.spec.mjs --project=web`. Playwright launches an isolated Chromium test browser with `--disable-features=WebRtcHideLocalIpsWithMdns` for this case. For two separate persistent browser processes, use `TEST_DIRECT_CDP_A` and `TEST_DIRECT_CDP_B` with their respective endpoints, and `TEST_CDP_ENDPOINT` to connect the standard fixture to an existing browser. Keep these profiles for one process restart, then run the same case with `TEST_DIRECT_REOPEN_ONLY=1` to verify their persisted edits. Use disposable profiles and remove them after the test.

Local proof used two separate, headless Brave 1.99.57 (Chromium 157.0.8103.79) profiles on one Linux host. With the default mDNS setting, both signed descriptions verified and each browser gathered host candidates, but ICE stayed `new` and the channels did not open. A standalone offer/answer probe reproduced that outcome. Launching the disposable proof browsers with `--disable-features=WebRtcHideLocalIpsWithMdns` produced real numeric host candidates. Both the standalone probe and the routed app then connected over a UDP host-to-host ICE pair with zero ICE servers. The application consumes the browser descriptions as generated. Default mDNS interoperability on this host, separate-host exchange and Android qualification remain open.

## Routed browser and Android exchange

Build the web app as above. Build and install the native app on a fresh, owned Android target. The x86_64 debug procedure uses the pinned native bindings, Expo Android prebuild, and the cached SDK/NDK described in the [native Android harness](../../../spikes/loro-storage/native/README.md). Build the Expo Router app at the repository root instead of the harness app. For a standalone debug APK, set `debuggableVariants = []` in the generated `android/app/build.gradle` React block and use the harness build command with `LORO_PROJECT_ROOT` set to this checkout. The resulting Android package is `com.creativecooking.app`.

1. Open **Start fresh local preview** on both devices and review and accept the local household policy. In Settings, open **Show device identity** and **Invite or join a household**. The Android device is the recipient for this run. Its **Share device identity file** exports the same public JSON as **Public device identity**. Enter that JSON in the browser’s **Recipient public identity** field and select **Prepare current-cooking invitation**.
2. On the browser, select **Show public household authority** after preparing the invitation. On Android, paste the browser’s **Public household authority** JSON into **Household authority bundle**, or import a JSON file with **Choose household authority file**. Compare and enter the browser’s **Household root to compare** and **Household head to compare** separately. Select **Verify and accept public authority**.
3. On Android, select **Join invitation**. Transfer the browser’s **Public invitation message** as text or a JSON file and compare the **Invitation verification code** separately. Enter that code on both devices and choose **Start or resume device verification**. Exchange the current **Your verification message** at each of the three phases and select **Continue device verification** on both devices. The Android **Share verification message file** and **Choose verification message file** carry the same JSON.
4. In the browser, choose **Admit and download encrypted household file**. Transfer `creative-cooking-household.bin` and import it via **Choose encrypted household file** on Android. Reopen the browser workspace to load the new authority. In Android’s **Show device identity** section select **Open this shared household**. Check that both apps show the same household and that any seed items are visible. Make a distinct local cooking edit on each device and wait for **Saved locally** before opening the direct controls.
5. In Settings, select **Exchange cooking updates directly** on both devices. Start a connection in the browser and choose **Create connection offer**. Transfer `creative-cooking-direct-offer.json` or the equivalent text to Android. Select **Answer a connection** and **Choose connection message file**, or paste the offer in **Direct connection offer**. Select **Verify offer and create answer**. Use **Share connection message** on Android to hand off `creative-cooking-direct-answer.json`, or copy its text. Import or paste it in the browser and select **Verify connection answer**. Keep both settings screens open while exchanging the messages.
6. Compare both displayed **Direct verification code** values. Enter an intentionally incorrect code on one device and verify rejection. Enter the correct code on one device and verify that sending stays unavailable while the second device has yet to confirm. Confirm on the second device and wait for **Direct connection verified on both devices**. Use **Send cooking updates** in each direction. Check that both peers show separate stored and applied receipts and that both pantry views show both edits. Open another verified session and send again to verify that the applied objects are skipped. Terminate and relaunch the Android process, and reopen the browser profile, to check selection and convergence after restart.
7. Make another local edit and use **Exchange encrypted cooking files**. The Android **Share encrypted update** control and the browser **Download encrypted update** control export the same raw encrypted object as `creative-cooking-update.bin`. Transfer it and use **Choose encrypted cooking update**. Check the other pantry after import. Replay the file and check that the edit appears once. For a retained-update check, import a dependent edit before its earlier update, apply the earlier one, and select **Retry retained update**.

An Android Documents provider can expose the exchanged files in Downloads. On a test emulator, file handling can be observed by placing the browser exports in Downloads and reading the app’s own exported cache files after invoking its share sheet. Continue through the regular app controls for verification and authorization. No private key, authority record, or local cooking data needs to be inserted for the proof.

If Android reports a selected-household storage error, **Return to original local household** on the locked screen explicitly changes the selection after verifying the original workspace. After restoring the joined household’s storage, select **Open this shared household** to return to it. An activated household with a missing counter must stay locked until its existing counter is recovered.

For source-level checks, run `agent-heavy -- env NATIVE_PROOF_DIR="$LORO_SCRATCH" node --experimental-strip-types --test src/loro/native/bootstrap-core.test.mjs src/loro/native/choice-core.test.mjs src/loro/native/sequences.test.mjs src/loro/transport/direct-signal.test.mjs` with an empty task scratch directory. The checks exercise real signed admission with SQLite, recovery after interrupted enrollment, running on an established workspace with the prior metadata layout, and exact native signaling comparison. The Android APK, platform WebRTC negotiation, and Android process restart are separate device evidence.
