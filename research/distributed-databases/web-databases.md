# Distributed database alternatives: current primary-source review

Reviewed 2026-10-15. This lane covers actual databases and sync stacks, separately from Matrix, Jazz, or independent authorization engines. This is source qualification, not a claim that any candidate has passed a Creative Cooking runtime bake-off. GitHub heads are evidence pins, not automatically recommended production versions. Repository metadata is saved in `/workspace/work/db-web-primary/*json`.

## Recommendation from this lane

**PowerSync + Postgres/Supabase is the leading pragmatic trusted-server candidate. PouchDB + CouchDB is a credible mature, permissively licensed comparator. Evolu 8 is a particularly relevant actively developing E2EE database challenger.** RxDB + Supabase is credible where its premium native storage cost and document model are acceptable. Electric + TanStack DB has improved substantially and should remain a bounded challenger, rather than being dismissed using old Electric write-path assumptions. These replace or reshape the existing Automerge storage approach; retaining Automerge is a preference to test, not grounds to hide databases that may reduce overall engineering.

Two trust lanes must stay visible: (1) operator-readable database + server-enforced authorization, versus (2) blind relay + cryptographic read/write capabilities. The first lane already handles multi-household membership and recipe scopes with standard authorization; it does not solve operator confidentiality. The second reduces server trust but currently has larger membership/invitation/removal/recovery gaps. The user has not selected server blindness as a mandatory condition in this renewed comparison.

For all candidates, choose a scope per household, retain explicit selected recipe copies and provenance, and implement combined errands as queries over authorized household scopes. Do not make a combined view into a new sharing group. No system can revoke plaintext already retained by an offline former member. Tests must instead distinguish future delivery denial, rejected queued writes, and what is removed from a cooperating device after reconnect.

## 1. PowerSync + Postgres/Supabase — first trusted-server qualification

Evidence pin: service [`fff5024cdee75f7c3ec578b4a1796763b3736bdd`](https://github.com/powersync-ja/powersync-service/tree/fff5024cdee75f7c3ec578b4a1796763b3736bdd), committed Oct14; service release [1.27.0 Oct6](https://github.com/powersync-ja/powersync-service/releases/tag/v1.27.0). JS/RN pin [`582babec1e676d9c4b90bd8d5311ec32055d68fa`](https://github.com/powersync-ja/powersync-js/tree/582babec1e676d9c4b90bd8d5311ec32055d68fa), Oct14, RN package2.3.1. Active development is verified, not inferred from stars.

- Actual local SQLite, durable queued offline writes, incremental server catch-up and browser/RN SDKs. A relay holds data between non-overlapping client sessions; simultaneous device presence is unnecessary.
- Use household membership tables with reader/editor/admin roles. Download **Sync Streams** join/filter on memberships; upload API or Supabase RLS authorizes writes. [RLS and streams are separate enforcement paths](https://docs.powersync.com/integrations/supabase/rls-and-sync-streams): download filters do not authorize uploads. Membership changes must alter server-evaluated scopes, not merely JWT household claims allowed to remain stale indefinitely.
- [Sync Streams are GA](https://releases.powersync.com/announcements/sync-streams-are-now-generally-available). New cloud organizations use streams; [legacy Sync Rules no longer receive security fixes](https://releases.powersync.com/announcements/our-plan-for-phasing-out-sync-rules). Use a current supported service and current stream compiler. The service changelog includes historical authorization-filter fixes; run actual negative access tests for our specific joins instead of assuming compiler correctness.
- The standard system trusts source DB/sync service with plaintext. TLS or local SQLCipher does not make household replication E2EE. Authentication/recovery can use established Supabase/OIDC accounts; the app does not need group encryption keys in this lane.
- [Conflict handling is explicitly server-authoritative](https://docs.powersync.com/handling-writes/handling-update-conflicts). App backend drains idempotent PUT/PATCH/DELETE; simple behavior is last server-received update per field. Shopping checks/quantity/delete semantics and recipe conflict preservation remain app decisions. Treat independent list rows as separate records, not a whole-list JSON blob. Automerge/Yjs blobs can be carried, but this adds dual persistence and should be justified by observed recipe editing requirements.
- App owns schema, household/invitation lifecycle, role rules, write connector, idempotence, rejection/recovery UX, and attachment strategy. This is conventional backend work, not a custom transport or cryptographic protocol.
- SDKs Apache2. Service [FSL1.1-ALv2](https://github.com/powersync-ja/powersync-service/blob/fff5024cdee75f7c3ec578b4a1796763b3736bdd/LICENSE), each version changes to Apache2 after two years; competing-service restrictions apply before then. Cloud and self-host paths exist. Postgres data and local SQLite create credible exit routes, with sync queue/state still vendor-specific.

Minimal test: two SQLite clients plus local/self-host service and Postgres; household membership join, stale token removal, forged household ID writes, offline cold restart, concurrent different-field and same-field updates, rejected write queue survival, all-data export. Then compile the official RN integration in our Expo57/RN0.86 generation. No feature-rich UI required.

## 2. PouchDB + CouchDB — mature independent baseline

Pins: [PouchDB `27de91f1105a8074ddd06f5a23156dd99c4eb016`](https://github.com/apache/pouchdb/tree/27de91f1105a8074ddd06f5a23156dd99c4eb016), Aug25; [CouchDB `d3884102b5a836f022d7d6a730ab29305d6e098a`](https://github.com/apache/couchdb/tree/d3884102b5a836f022d7d6a730ab29305d6e098a), Oct13. PouchDB latest GitHub release9.0.0 is from June2024, but Apache-hosted source development continues; age of release alone is not abandonment evidence.

- Browser persistent adapters and Couch replication solve offline writing/non-overlap sync. Couch stores conflicting document revisions; a deterministic winner is **not** an automatic semantic merge. App can expose/preserve losing recipe edits. Separate shopping item documents reduce contention; ordered recipes need explicit modeling.
- Couch [database members/admins](https://docs.couchdb.org/en/stable/intro/security.html) govern read boundaries. Use **one database per household** and, where needed, a personal database. `validate_doc_update` enforces application writer/admin roles; it runs on replicated writes. Member accounts need not be server administrators. Do not confuse replication filters with read security: permitted DB readers can fetch the entire DB. Explicit cross-household recipe copies fit well; arbitrary per-recipe sharing inside a household would require additional databases or an authorized service/projection.
- Trusted-server plaintext, account/cookie authentication and ordinary account recovery; encrypted local storage is separate from E2EE. App owns provisioning memberships, invitations, write validation, conflict UX, purge-on-signout/removal behavior and backups.
- Native is more promising than old articles imply: active [OP-SQLite adapter4.4.2](https://github.com/craftzdog/pouchdb-adapter-react-native-sqlite/releases/tag/v4.4.2), Sept17. Reviewed source [`0e99dfd0d72b97ed35a8d4da500c89e3e2e0ab76`](https://github.com/craftzdog/pouchdb-adapter-react-native-sqlite/tree/0e99dfd0d72b97ed35a8d4da500c89e3e2e0ab76), Oct14, develops against RN0.87.1 and OP-SQLite18.2.3. [README](https://github.com/craftzdog/pouchdb-adapter-react-native-sqlite/blob/0e99dfd0d72b97ed35a8d4da500c89e3e2e0ab76/README.md) documents Hermes design-doc function serialization workaround and Metro binary-attachment fixes. These are concrete integration checks, not grounds to assert native is impossible. Avoid stale `craftzdog/pouchdb-react-native` fork (last source2022).
- Core DBs Apache2, native adapter MIT. Self-host without a mandatory commercial control plane. Largest tradeoffs: document joins, conflict handling and database provisioning; less modern typed developer experience than newer alternatives.

Minimal test: household A/B Couch DBs, reader/editor/admin accounts, negative direct `_all_docs` and `_bulk_docs` attempts, two offline Pouch replicas, conflicting recipe revisions, DB-per-household combined errands query, membership removal with previously issued session, native cold restart/attachment smoke. It provides a useful cost baseline even if a newer system wins.

## 3. Evolu 8 — active E2EE/database challenger

Pin [`f48a2580f44e74ee5362dd0bcb0ad86a675f4f3b`](https://github.com/evoluhq/evolu/tree/f48a2580f44e74ee5362dd0bcb0ad86a675f4f3b), Oct14. Common8.22.4; RN16.1.5. MIT. Its [current native package](https://github.com/evoluhq/evolu/blob/f48a2580f44e74ee5362dd0bcb0ad86a675f4f3b/packages/react-native/package.json) develops against **Expo57.0.28/RN0.86.3**, matching our generation. More relevant initial native evidence than a bridge two React Native generations behind.

- SQLite, SQL query builder, CRDT changes, encrypted owner scopes, self-hostable replaceable relays; E2EE payloads with visible owner/timing metadata. Database and synchronization are actual library responsibilities, not homemade encrypted chat envelopes.
- `AppOwner` is personal identity; `SharedOwner` provides read/write scope; `SharedReadonlyOwner` contains read-only encryption capability. Multiple owners are an architectural match for multi-household plus selected recipe scopes. Recovery mnemonic/owner secrets can restore data; app must design secure storage, user onboarding and recovery UX.
- **The current API types are ahead of some runtime workflows.** [Protocol.ts1281](https://github.com/evoluhq/evolu/blob/f48a2580f44e74ee5362dd0bcb0ad86a675f4f3b/packages/common/src/local-first/Protocol.ts#L1281) explicitly marks read-only sync TODO and returns `Readonly` when no write key. [Evolu.ts](https://github.com/evoluhq/evolu/blob/f48a2580f44e74ee5362dd0bcb0ad86a675f4f3b/packages/common/src/local-first/Evolu.ts) marks owner/database deletion unimplemented. A shared write capability alone is not a verified household administrator/member removal protocol.
- The [Sept1 release explanation](https://www.evolu.dev/blog/evolu-8-is-released) explicitly says the local-first platform is not yet recommended generally: public multi-owner experience, passkey local auth and coordinated deletion unfinished. Core used in Trezor Suite through custom integration is evidence of use, not proof of our group workflow. Evolu7→8 automatic migration also not ready.
- App owns public identity/verified invitation, owner-secret distribution, role UI and potentially rotation/re-scope on removal unless upstream workflow is completed. Do not promise admin-only removal or forward secrecy using shared static keys without a source-backed implementation.

Minimal qualification first asks the expensive question: can two distinct app owners actually use a shared writable household over a current relay, persist/restart and recover? Next prove genuine read-only sync and removal/re-key behavior with existing public APIs. If gaps require completing a sizeable upstream subsystem, report that effort and preserve it as an active research challenger; do not invent a crypto protocol to make the demo pass.

## 4. RxDB + Supabase — flexible document database with established server ACL

Pin [`a70c5205c8d1d6621cf17dc32e5472747eeecc50`](https://github.com/pubkey/rxdb/tree/a70c5205c8d1d6621cf17dc32e5472747eeecc50), Oct14; release17.6.0 Oct5. Apache2 core; [premium storage/plugins](https://rxdb.info/premium/) have separate commercial terms. Budget premium Expo Filesystem/SQLite storage rather than presenting a trial native adapter as production qualification.

- Reactive local document collections, browser durable stores, RN adapters, checkpoints and retryable push/pull. Official [Supabase replication](https://rxdb.info/replication-supabase.html) implements resumable pulls, guarded pushes and tombstones; missed realtime events do not become the sole source of history.
- Supabase auth + Postgres membership RLS controls household read/write/admin, with explicit immutable household IDs and administrator-only membership changes. App owns policies and invitation UX, but need not build a generic permission engine. Recipe copies are rows in destination scope. Local queries are document/Mango rather than full SQL relational joins.
- RxDB's default conflict handler selects master state; custom conflict semantics or its CRDT plugin must be deliberately tested. Claims of automatic sync do not establish preservation of independently edited recipe fields.
- [Encryption wraps local storage](https://github.com/pubkey/rxdb/blob/a70c5205c8d1d6621cf17dc32e5472747eeecc50/docs-src/docs/encryption.md); collection consumers see decrypted fields and normal replication is not automatically E2EE. Server-blind groups still need key distribution/rotation; do not count an encrypted database password as a complete household E2EE stack.
- App owns membership model, policies, schema migrations, conflict policy, replication access-loss cleanup. RLS hiding a formerly visible row is not automatically a tombstone deliverable to the revoked client: test stale local data and stop/restart or rescope replication on authorization changes.

Minimal test mirrors PowerSync, plus production native storage licensing and deleted/revoked row checkpoint behavior. This is credible, not a default win over PowerSync's SQL model.

## 5. Electric + TanStack DB / PGlite — evolving composable option

Electric pin [`3f9809fb0bd894cb74470d434749673492ad7acf`](https://github.com/electric-sql/electric/tree/3f9809fb0bd894cb74470d434749673492ad7acf), Oct6, Apache2. PGlite [`550943fbca8c40a0185a2d02d11afdcea97fa869`](https://github.com/electric-sql/pglite/tree/550943fbca8c40a0185a2d02d11afdcea97fa869), Oct14,0.5.10, Apache2. TanStack DB [`3a98e0062fda2084596d218c14609f30dbef365a`](https://github.com/TanStack/db/tree/3a98e0062fda2084596d218c14609f30dbef365a), Oct14, MIT. Current Electric docs are at `electric.ax`; legacy bidirectional `electrify`/Expo examples describe a different generation.

- [Electric Sync is the Postgres read path](https://electric.ax/docs/sync/), not a complete offline write/authority system. [Authenticated proxy shapes](https://electric.ax/docs/sync/guides/auth) plus a normal authorized mutation API can enforce household membership. Never expose an arbitrary client-controlled shape filter as permission enforcement.
- Crucially, current [TanStack DB offline transactions](https://github.com/TanStack/db/blob/3a98e0062fda2084596d218c14609f30dbef365a/docs/guides/offline-transactions.md) provide persistent outbox/retry and a React Native entry point; current [SQLite persistence](https://tanstack.com/db/latest/docs/guides/sqlite-persistence) has RN OP-SQLite support. This is a concrete composable route; saying Electric has no offline path would be inaccurate. It still requires our idempotent write API and reconciliation/rejection policy.
- PGlite gives browser/WASM Postgres and Electric materialization. Do not infer Hermes support from a browser WASM demo. Native may instead use TanStack's SQLite adapters and the TS Electric client; verify a shared adapter boundary rather than requiring identical underlying storage engine.
- Trusted server; no built-in group E2EE lifecycle. Accounts/recovery can come from existing auth provider; app owns scope proxy, membership and server writes. More assembly than PowerSync, but active development and permissive licenses justify a narrow test if simple composition works.

Minimal qualification: prove persisted optimistic edits survive browser/native process restart, replay idempotently, reconcile with incoming shape updates, and do not become stuck on a removed membership. Stop if we need to build a missing sync engine rather than compose the supplied outbox.

## 6. Zero — active, native supported, deliberately online-first

Pin [`617e92f298b0f9547478b9e14bee11f785f45b30`](https://github.com/rocicorp/mono/tree/617e92f298b0f9547478b9e14bee11f785f45b30), Oct14, Apache2. Official [React Native/Expo SQLite support](https://zero.rocicorp.dev/docs/react-native) is present. Current [server queries/mutators](https://zero.rocicorp.dev/docs/auth) handle authorization; don't assess only obsolete static permission APIs.

However, [current connection docs](https://zero.rocicorp.dev/docs/connection) explicitly reject writes in disconnected/error/needs-auth state and discourage prolonged offline operation; a brief connecting queue is not durable week-long local-first write support. Therefore no primary bake-off slot for offline grocery editing unless upstream changes this contract. This is a requirement mismatch, not an alpha stigma or native-support rejection.

## 7. InstantDB — fits technically, original team/cloud exiting

Pin [`b97a1164fdc51f13498df68c3188801576c7b27d`](https://github.com/instantdb/instant/tree/b97a1164fdc51f13498df68c3188801576c7b27d), Sept28, Apache2. Built-in relational queries, offline persistence (IndexedDB/AsyncStorage), reactive transactions, auth and expressive namespace/linked-data permission rules would be a good functional fit.

But official [team announcement](https://www.instantdb.com/essays/instant_team_joins_openai) says team joining OpenAI, new cloud signups closed and **Cloud shuts down Aug31,2027**. Self-hosting/migration code remains. Do not label the open-source code unusable, but new adoption would depend on credible ongoing independent maintenance or owning the fork. This conflicts directly with the user's desire for forward-moving development and deserves a clear downgrade, not a hidden omission.

## 8. Triplit — excellent conceptual match, weak current maintenance evidence

Pin [`d3029ee13e747abeeab8cf5bf64427f77a142e1f`](https://github.com/aspen-cloud/triplit/tree/d3029ee13e747abeeab8cf5bf64427f77a142e1f), last source commit Sept11,2025; repository pushed Jan2026, not archived. Root AGPL3; inspect package distribution terms if adopting.

Source contains offline relational/triple queries, multi-writer sync, IndexedDB and Expo SQLite, plus [JWT roles and per-operation permission filters](https://github.com/aspen-cloud/triplit/blob/d3029ee13e747abeeab8cf5bf64427f77a142e1f/packages/docs/src/pages/schemas/permissions.mdx). Checks run on server; offline forbidden writes are rejected later. This is trusted-server authorization, not E2EE. Household membership relation filters are plausible. But no recent active development evidence; [site availability issue406](https://github.com/aspen-cloud/triplit/issues/406) and dormant source outweigh older marketing. Retain as technically relevant but not a primary forward-moving contender unless maintained successor appears. No shutdown announcement was verified, so do not invent one.

## 9. Newly discovered: SQLiteAI SQLite-Sync — real CRDT/RLS stack, restrictive transport exit

Core pin [`53843ed9577ea13e22a65e73fbbcc791ce3d85bb`](https://github.com/sqliteai/sqlite-sync/tree/53843ed9577ea13e22a65e73fbbcc791ce3d85bb), Oct1;1.2.0 Sept28. [Native wrapper](https://github.com/sqliteai/sqlite-sync-react-native/tree/bc1d30b0632de1d4b339171f254028b75bbce617), Sept28, MIT wrapper. Actual SQLite extension supports CRDT sync, Expo/RN development builds and WASM; Postgres/Supabase extension supports RLS. Column-batch apply and denied-write transaction semantics are described in [pinned RLS source docs](https://github.com/sqliteai/sqlite-sync/blob/53843ed9577ea13e22a65e73fbbcc791ce3d85bb/docs/postgresql/reference/rls.md). This merits discovery credit and could avoid bespoke conflict transport.

However, [modified Elastic2 license](https://github.com/sqliteai/sqlite-sync/blob/53843ed9577ea13e22a65e73fbbcc791ce3d85bb/LICENSE.md) explicitly requires commercial permission to replace, bypass, modify or reimplement its Network Layer even for OSS. Commercial production/managed service use also requires a commercial license. [Self-host Postgres quickstart](https://github.com/sqliteai/sqlite-sync/blob/53843ed9577ea13e22a65e73fbbcc791ce3d85bb/docs/postgresql/quickstarts/postgres.md) still registers a CloudSync dashboard workspace/backend. Thus self-hosting the source database does not establish an independent, freely replaceable sync service. It is a viable commercial trusted-server candidate if those terms are accepted, but a poor first choice for the user's explicit later-switch/exit concern. No independent cryptographic household key lifecycle verified.

## Bounded qualification plan

Do not build nine full apps. Use the same minimal schema: households, memberships, shopping_lists, shopping_items, recipe_copies, requirements, plus provenance and stable IDs. Two households, three users (admin/editor/reader), two clients never online simultaneously, one uninvited adversarial client. Each adapter exposes create/read/update/delete, subscribe, flush, export/import, offline state and rejected-write status.

1. First qualify PowerSync and either PouchDB or RxDB as trusted-server baseline; use local containers/synthetic data and official SDKs. Pick Pouch if permissive independence is weighted most; RxDB if document reactivity/adapter flexibility is more valuable.
2. In parallel narrowly qualify Evolu multiple-owner sharing/read-only/removal using its real SDK. Keep its active upstream trajectory visible even if remaining group features prevent immediate adoption. Compare against the other lane's actively developed E2EE candidates, not only Jazz Classic.
3. Electric/TanStack gets a small composition check, not an entire third backend. Only expand if persistence/outbox/native integration is demonstrably simpler or more flexible.
4. Evaluate library license, running services, app-owned policy/code and migration cost alongside failures. Existing accountless personal use must remain available; sharing can introduce an account with a deliberate local-data adoption step.
5. End with actual executed evidence, unknowns and the trust choice needed from the user. No ARM64 device means browser and available emulator qualification must be labeled accordingly. Do not invent native device evidence or silently select a trust model.
