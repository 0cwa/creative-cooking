# Distributed database / CRDT ecosystem review

Source review: 2026-10-15. This lane checked repositories, pinned source, release/npm metadata and implementation boundaries; no Creative Cooking runtime qualification was executed. Activity means the public repository's latest push and is not a maintenance guarantee.

## Recommendation from this lane

**p2panda deserves a first-class, tightly bounded exploratory spike alongside the integrated stacks in other lanes.** It is a much better conceptual match than repurposing chat: typed immutable signed operations, durable causal replication, genuinely offline group authorization, and group E2EE. It can carry Automerge changes without replacing Automerge. Its current high-level implementation is progressing rapidly, not abandoned; adopting an exact development commit could be sensible for feasibility. However, implementation maturity, browser deployment and the actual mobile bridge need proof. There are concrete present limitations to expose rather than wave away.

**Hypercore / Autobase / HyperDB is the second credible database-native ecosystem to consider**, particularly if native mobile takes precedence over a full browser PWA. Real Expo embedding, blind storage peers and pairing exist. This ecosystem avoids inventing a transport, but does not by itself avoid owning household key/role/recovery orchestration. It is less compelling for this app than p2panda's integrated group model.

**Loro is active and has more platform/transport support than a CRDT-only dismissal suggests**, including a native RN binding and new E2EE sync protocol. Nonetheless its protocol explicitly excludes key agreement. Changing Automerge to Loro does not solve the present identity/authorization question. OrbitDB similarly has real durable replication and mutable write ACLs, but encryption/key management remains the weaker link. Fireproof is a legitimate encrypted database but current public activity and verified group lifecycle are weaker than stronger candidates.

## p2panda — promote to exploratory shortlist

Primary pin: [p2panda/p2panda c99f5014836cb26ba96688baafad0d4cdb6e61d7](https://github.com/p2panda/p2panda/tree/c99f5014836cb26ba96688baafad0d4cdb6e61d7), last pushed Oct 14. Dual MIT / Apache-2.0. Latest published GitHub release [v0.7.1](https://github.com/p2panda/p2panda/releases/tag/v0.7.1), Aug 21. **Main is 311 commits ahead of v0.7.1**: do not attribute all current-main APIs to the released crate.

- High-level Rust API orchestrates iroh QUIC networking, discovery, bootstrap, topic-scoped partial replication, signed single-writer operation logs, causal ordering, pruning, SQLite persistence and durable stream cursors. Payloads are data-type-agnostic; Automerge binary changes fit without a second application CRDT engine.
- [p2panda-auth README](https://github.com/p2panda/p2panda/blob/c99f5014836cb26ba96688baafad0d4cdb6e61d7/p2panda-auth/README.md) provides Pull / Read / Write / Manage roles, add/remove/promote/demote, nested groups and generic conditions. Only Manage can mutate membership.
- Offline authority is real source, not a central-server ACL marketing claim: the [strong-remove resolver](https://github.com/p2panda/p2panda/blob/c99f5014836cb26ba96688baafad0d4cdb6e61d7/p2panda-auth/src/group/resolver.rs) filters concurrent removed-member authority operations and dependent delegations, handles mutual removal cycles and remove-vs-readd. Application data acceptance/replay must still be tested; do not infer that every already-materialized application change automatically rolls back correctly.
- [p2panda-spaces](https://github.com/p2panda/p2panda/blob/c99f5014836cb26ba96688baafad0d4cdb6e61d7/p2panda-spaces/README.md) integrates group ACL and encryption, multi-device nested identities, private space identifiers, shared groups across encryption boundaries. Data encryption preserves historical keys for offline reads, rotates on membership removal; message encryption offers different forward-secrecy behavior. Retaining data keys is a deliberate database requirement, not erasure of past access.
- This is now integrated into [high-level spaces API](https://github.com/p2panda/p2panda/tree/c99f5014836cb26ba96688baafad0d4cdb6e61d7/p2panda/src/spaces), including publish/add/remove/promote/demote, SQLite space state and key-secret persistence. Some lib.rs prose still says persistence is forthcoming; current implementation source is more informative. [Key secret store](https://github.com/p2panda/p2panda/blob/c99f5014836cb26ba96688baafad0d4cdb6e61d7/p2panda-store/src/key_secrets/sqlite.rs) serializes secrets as CBOR into SQLite; secure at-rest storage/recovery is a separate product/platform integration concern.

Concrete qualification gaps:

1. **Cross-household metadata leakage:** [repair.rs](https://github.com/p2panda/p2panda/blob/c99f5014836cb26ba96688baafad0d4cdb6e61d7/p2panda/src/spaces/repair.rs) currently defaults to Global repair, copying all known group auth operations into a space, even groups not belonging to that space. Partial strategy exists but initial group discovery is explicitly unimplemented, so source says all spaces use Global for now. This matters directly to several unrelated households on one device.
2. **Manual secret UPDATE is unimplemented:** [forge.rs](https://github.com/p2panda/p2panda/blob/c99f5014836cb26ba96688baafad0d4cdb6e61d7/p2panda/src/spaces/forge.rs) has an explicit unimplemented branch for UPDATE. This is distinct from claiming removal never rotates keys; removal has its own existing flow.
3. **High-level conditional permissions not wired:** [types.rs](https://github.com/p2panda/p2panda/blob/c99f5014836cb26ba96688baafad0d4cdb6e61d7/p2panda/src/spaces/types.rs) sets `AuthCapabilities = ()` and says high-level API does not do anything with auth capabilities yet. Household-scoped roles can still use separate spaces; arbitrary per-recipe/path conditions require lower-level work or upstream development.
4. Native Rust can run on mobile, but [experimental FFI](https://github.com/p2panda/p2panda-ffi) currently documents Node.js / Python / Go via UniFFI, not a qualified React Native/Expo package. Producing a small RN UniFFI bridge is plausible engineering, not new protocol design. Need discover whether end-to-end Spaces APIs are exported, rather than just topic streaming. Browser-native stack / persistent WASM+network path was not verified. Iroh browser capabilities alone do not establish the full p2panda browser stack.
5. Account onboarding, verified identity exchange, a lost-all-devices recovery UX and durable offline rendezvous policy are not turnkey app features established by this source review. The group encryption machinery exists; distinguish that from complete consumer account/recovery flows.
6. Under active API development with no production stability promise. No independent audit of this exact new integrated stack was verified.

Best spike: pin the exact current-main commit, run two Rust peers with persistent SQLite + Automerge payloads, exercise household create/read/write/manage, removal concurrent with offline edit and clean restart. Simultaneously attempt the smallest RN and browser integration. Stop before implementing app-owned alternative cryptography if the current metadata/privacy or platform gap demands upstream work beyond a bounded trial.

## Hypercore / Autobase / HyperDB — credible native-oriented alternative

- [Hypercore 9c9cc3d8937b6ae539fbacf52a7090cd732a1945](https://github.com/hypercore-protocol/hypercore/tree/9c9cc3d8937b6ae539fbacf52a7090cd732a1945), MIT, Oct 15: signed append-only logs, sparse durable replication, optional at-rest content encryption.
- [Autobase 846103a277edc6ef309c95765e95f918a6ec1b60](https://github.com/holepunchto/autobase/tree/846103a277edc6ef309c95765e95f918a6ec1b60), Apache-2.0, Sep 8: multiwriter linearized views, addWriter/removeWriter, indexer membership and optimistic writes. App supplies deterministic apply/view behavior. **Writer membership is not a complete user/admin role model**; app's apply handler must authenticate membership-changing commands.
- [HyperDB ead3b18277ed16ff79f8289da0d32fcdf3f7671e](https://github.com/holepunchto/hyperdb/tree/ead3b18277ed16ff79f8289da0d32fcdf3f7671e), Oct 14: generated schemas, collections, indexes; Hyperbee replicated engine or local RocksDB engine. This is a real database option rather than raw networking alone.
- [Blind pairing](https://github.com/holepunchto/blind-pairing/tree/c421d80cc59aad8ad2b6fe717d11344d70d305f3) has invite candidates, user data and explicit member confirmation; [blind-peering](https://github.com/holepunchto/blind-peering/tree/856e2da2c0de670e66421f55cf93f87e535251dc) requests blind mirrors for cores/autobases and push notifications, Oct 13. These are usable existing components, not complete household key rotation/recovery.
- [react-native-bare-kit a9ca02a73f5c7451138f6c999a63a2de54442794](https://github.com/holepunchto/react-native-bare-kit/tree/a9ca02a73f5c7451138f6c999a63a2de54442794), Apache-2.0, Oct 9, embeds a Bare worklet with IPC. [bare-expo example e025a901ed1d582aec4a9e0a9452f5b93e6c1620](https://github.com/holepunchto/bare-expo/tree/e025a901ed1d582aec4a9e0a9452f5b93e6c1620) explicitly demonstrates Expo iOS/Android. Native addon linking remains app-owned; full browser PWA equivalent was not established.

Autobase `encryptionKey` is an app-provided shared key. Removing a writer does not by itself prove exclusion from future read keys; account/device recovery, group key distribution/rotation and role hierarchy remain integration obligations. Strong active development and actual native route justify keeping it in the comparison, but it is not the shortest route to audited household E2EE permissions. Using it beneath Automerge is possible but adds two replication semantics; likely use its own event/view model or stay with Automerge plus a group-oriented stack.

## Loro ecosystem — active engine plus transport, key agreement remains external

[Loro 4f60d921d820de3522624a436de77f994a6622b8](https://github.com/loro-dev/loro/tree/4f60d921d820de3522624a436de77f994a6622b8), MIT, Oct 9, supports Rust, WASM JS and Swift. [Loro Mirror](https://github.com/loro-dev/loro-mirror/tree/97fd2f0f79aa797e16829435b08727cd6212787b), Sep 10, adds schema/state management rather than identity authority.

**There is an official native binding**: [loro-react-native 8fad8d61c11c23e7c57999533d637d316465ffc1](https://github.com/loro-dev/loro-react-native/tree/8fad8d61c11c23e7c57999533d637d316465ffc1), MIT, July 21, UniFFI, iOS/Android build scripts. Its source package is 1.13.2 and development RN 0.79.2; npm latest was 1.10.3, Dec 2025. Verify actual package/core pin compatibility before trial, not assume npm latest is current source.

[Loro Protocol 1776306b473e2dd618975383c498a282851c1837](https://github.com/loro-dev/protocol/tree/1776306b473e2dd618975383c498a282851c1837), MIT, Sep 30, multiplexes rooms with acknowledgements and fragmenting large updates. TS server offers persistence hooks/read-or-write auth callback; Rust server optional SQLite snapshots. ELO provides AES-GCM encrypted document transport with server-blind payloads and cross-language tests. **README explicitly says “Keys and key agreement are application-provided and out of scope.”** Thus it still needs a separate group authority/recovery solution. A future engine alternative, not an immediate answer to key-management ownership.

## OrbitDB / IPFS / libp2p — real P2P database, incomplete group confidentiality

[OrbitDB 2ee8387240dc0220266d170eac608a2d54de709e](https://github.com/orbitdb/orbitdb/tree/2ee8387240dc0220266d170eac608a2d54de709e), MIT, last public push May 14; npm 4.0.0 same day. Browser/Node support, IPFS storage plus libp2p PubSub Merkle-CRDT replication, documents / keyvalue / indexed keyvalue / events.

[Mutable access controller](https://github.com/orbitdb/orbitdb/blob/2ee8387240dc0220266d170eac608a2d54de709e/src/access-controllers/orbitdb.js) verifies signed identity writes and permits grant/revoke of write/admin-like capabilities. Root admin rights derive from the immutable access controller of the ACL database. This is meaningful write authorization, not a complete distributed account lifecycle or proven causal/offline removal policy.

[Encryption docs](https://github.com/orbitdb/orbitdb/blob/2ee8387240dc0220266d170eac608a2d54de709e/docs/ENCRYPTION.md) support payload/log encryption, including blind replicators. Its maintained [SimpleEncryption module](https://github.com/orbitdb/simple-encryption) is password AES-GCM/PBKDF2 and explicitly demonstration-only/unaudited. Private read access, verified invites, rekey on removal and device recovery therefore still require an external system. No qualified Expo bridge was established; web browser success does not automatically imply Hermes/Level/Helia compatibility. Keep lower priority unless decentralized content-addressed storage is itself a goal.

## Fireproof — encrypted embedded document DB, weaker lifecycle/activity evidence

[Fireproof 404e6c5c7f28109c103626c78da845eb95cabcfa](https://github.com/fireproof-storage/fireproof/tree/404e6c5c7f28109c103626c78da845eb95cabcfa), Apache-2.0, last public push May 7; npm latest @fireproof/core 0.24.19 Apr 15. Browser persistent JSON documents, live queries, content-addressed encrypted blob synchronization over commodity storage. Actual encrypted sync, not merely TLS.

Source tree contains cloud/dashboard authentication, tenant-ledger routing and a keybag, but that is not sufficient evidence of offline group member/admin authority, automatic removal rekey and recovery. README explicitly says default internal extractKey bypass remains and more secure key management is roadmap work. No qualified Expo storage/crypto adapter established. Not marked abandoned; public evidence is simply less current than p2panda/Loro/Hypercore, and it does not resolve our verified group-lifecycle needs yet.

## Automerge Repo and Yjs providers — trustworthy-server alternatives remain viable

[Automerge Repo 8b178e75ecca89f78465196ef786aa844da57aec](https://github.com/automerge/automerge-repo/tree/8b178e75ecca89f78465196ef786aa844da57aec), MIT, Oct 13: persistent adapters, document handles and pluggable network adapters, shareConfig/sharePolicy controls. These control willing peers' sharing, **not cryptographic authority against malicious connected peers**, absent authenticated transport and enforcement. [Reference sync server](https://github.com/automerge/automerge-repo-sync-server/tree/c357887cb7295ddd2399a679e4e75def2a284801), Sep 30, calls itself unsecured. It is not a household production service out of the box. No current official integrated Cloud account/group E2EE product was verified in this lane. Keyhive/Subduction is covered separately; archived @localfirst/auth remains unsuitable as the default maintained dependency.

[Yjs](https://github.com/yjs/yjs/tree/d01eefc997cf12d29d5aabea804df5f69c659a79), Oct 7, is active; [SyncedStore](https://github.com/YousefED/SyncedStore/tree/7234609d083baf07c866aa753690acded567facc) last public push Mar 2024 adds reactive state rather than ACL. [Hocuspocus bd288a4441fb60a663bbaf34660a490eb59dd6ea](https://github.com/ueberdosis/hocuspocus/tree/bd288a4441fb60a663bbaf34660a490eb59dd6ea), MIT, Oct 14, offers durable SQLite/database extensions, auth hooks and hosted Tiptap collaboration. [Y-Sweet 4f1909b2c3390ced54d32b82a673f4f7ee8ac780](https://github.com/jamsocket/y-sweet/tree/4f1909b2c3390ced54d32b82a673f4f7ee8ac780), README says MIT, last push Dec 2025, is a genuine S3-backed durable document store with client-token document access. Both offer realistic server-authorized collaboration; neither documented baseline establishes blind E2EE household groups with integrated key rotation/recovery. Their server-side CRDT materialization means the server can read the underlying document. A valid comparison if trusted-server sync is acceptable, but changing engines gains little if Automerge plus authenticated hosted storage already meets the product trust model.

Turso was discovered active Oct 14 [d808271a35472bd94d2f0efbc7bb69fab3be6b26](https://github.com/tursodatabase/turso/tree/d808271a35472bd94d2f0efbc7bb69fab3be6b26), MIT; SQL sync lane should assess its actual read/write sync and authorization scope. Do not infer household ACL from “sync” branding.
