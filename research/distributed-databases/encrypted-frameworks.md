# Broader encrypted distributed database/access review

Reviewed 2026-10-15. This lane covers Shelter/Chelonia, Peergos, Hyper Hyper Space v3, CoMapeo/Awana, Verida, GUN/SEA, Holochain, and Willow/Iroh. Other lanes own Jazz, DXOS, NextGraph, Anytype, Automerge/Keyhive and conventional database sync. This is source/API qualification; no application runtime or protocol security audit was performed here.

## Revised findings

The previous survey dismissed several candidates too early. Two concrete discoveries materially improve the comparison:

1. **Shelter's Chelonia is already a published reusable library**, `@chelonia/lib` 2.0.0, released September 30, with encrypted state contracts, files/KV/pubsub, key opcodes, durable server logs and persistent-action retry. Current `okTurtles/libcheloniajs` exists; assessing only the stale protocol implementation landing page was insufficient. Its current reference app implements actual member removal and remaining-member key redistribution. It merits a bounded browser + Expo import/protocol trial even though application integration is immature.
2. **Hyper Hyper Space v3 is an active implemented engine**, with peer sync, causal capabilities, SQLite/IndexedDB database projection and a newly added browser host. The v2 homepage warning is not grounds for rejecting v3. It merits a bounded causal authorization/database trial. It does **not yet prove a blind-storage group encryption lifecycle**: authenticated encrypted channels and signed causal write permissions solve different questions from encrypted replicas/key rotation.

**Peergos** is also considerably stronger than a generic encrypted-filesystem dismissal: current code exposes sharing groups, cryptographic read/write removal, hybrid post-quantum sharing and a new functional pre-1.0 Rust client. Its current advertised offline support is read/cache, and embedding its complete filesystem stack into Expo/PWA while adding conflict-safe writes is a larger adaptation than the browser reference product suggests.

An alpha label is not an exclusion in this review. The decision variables are actual missing capabilities, development trajectory, tractable integration and defensible authority/privacy semantics. Recent push timestamps alone are not a health score; substantive commit/release examples are recorded below.

## Shelter/Chelonia: the most promising overlooked existing key stack

Primary pins:

- Library commit `9c3afd2081d2fc216d7e8f713717b54079fbc6ac`: https://github.com/okTurtles/libcheloniajs/tree/9c3afd2081d2fc216d7e8f713717b54079fbc6ac
- Current library overview: https://github.com/okTurtles/libcheloniajs/blob/9c3afd2081d2fc216d7e8f713717b54079fbc6ac/README.md
- Actual published artifact manifest, 2.0.0: https://registry.npmjs.org/@chelonia/lib/2.0.0
- Current reference app `4c5d095763bb42b0c9b55bba210fcb98b60e172c`: https://github.com/okTurtles/group-income/tree/4c5d095763bb42b0c9b55bba210fcb98b60e172c
- Key operations: https://shelterprotocol.net/en/opcodes/
- Expiry/use-limited invites: https://shelterprotocol.net/en/invite-keys/
- Ordered durable event API: https://shelterprotocol.net/en/server-api/

The library README explicitly supplies encrypted contracts, encrypted files/KV/pubsub, persistent actions, and says **federation support coming soon**. Do not present federation as shipped just because the protocol calls itself federated. A single service can host several independent households without federation.

The important source evidence is stronger than API marketing. `frontend/model/contracts/group.js` implements `removeMember`: validates membership/removal authority, marks `cek` (contract encryption key) and `csk` (contract signing key) pending revocation, and later invokes rotation. `frontend/controller/actions/group.js::shareNewKeys` shares new keys only with ACTIVE profiles and encrypts each recipient's private keys against that identity's CEK. Failed distribution retries; members temporarily missed can request missing keys afterward. `inviteRevoke` exists. Rejoining code expressly considers removal while offline and avoids automatically rejoining.

Pinned source: https://github.com/okTurtles/group-income/blob/4c5d095763bb42b0c9b55bba210fcb98b60e172c/frontend/model/contracts/group.js and https://github.com/okTurtles/group-income/blob/4c5d095763bb42b0c9b55bba210fcb98b60e172c/frontend/controller/actions/group.js . This proves a real lifecycle implementation, not independently verified absence of vulnerabilities.

**Household policy is not ready-made.** Group Income has creator/proposal governance and app-specific Vue hooks; it is not a reader/editor/admin household library. We would define a small household contract and permission mapping using existing signing/key opcodes, or carry immutable Automerge changes inside encrypted contract actions. That is domain/access-policy code, which must be tested; it need not be a newly designed encryption protocol. Group Income source has TODOs for some admin checks; do not transplant its whole policy without review.

**Persistence needs deliberate wiring.** Library `src/db.ts` defaults to LIGHTWEIGHT_CLIENT mode: raw-event database primitives are mostly no-ops. Full mode defaults to in-memory `okTurtles.data`. The comments explicitly provide overriding `chelonia.db/get/set/delete/iterKeys/keyCount` for persistent storage. SQLite/IndexedDB adapters and root-state/outbox persistence are integration work, not presumed included defaults. `docs/journal.md` warns its optional redacted state-diff journal is not a raw-message backup. Source: https://github.com/okTurtles/libcheloniajs/blob/9c3afd2081d2fc216d7e8f713717b54079fbc6ac/src/db.ts and https://github.com/okTurtles/libcheloniajs/blob/9c3afd2081d2fc216d7e8f713717b54079fbc6ac/docs/journal.md .

Server `POST /event` rejects competing previous heads with HTTP409 and latest head/height. Clients need retry/resync; this is serialized contract authority, not inherently coordination-free authorization. Application may retain local optimistic edits but must not claim peer acceptance before server commit. Test removed/offline writers preserving rejected edits locally. Fresh-device login/identity restoration and forgotten-password recovery are distinct; protocol's password/unique-device discussion is not an implemented household recovery UX guarantee.

Platform: npm publishes ESM/CJS + TS, dependencies include TweetNaCl and scrypt-async, no required new native cryptography identified. Source uses Buffer, globals and dynamic `new Function` to evaluate contracts; Hermes compatibility and target bundler restrictions need a tiny proof. Browser reference app is real; no supported Expo integration was found. Library last default-branch commit Oct7 adds username validation; Sept29 fixes lightweight defaults; Sept30 release2.0.0. API pushed timestamp Oct14 includes nondefault activity. AGPL-3.0, with documented commercial dual-licensing contact. No independent current protocol/library audit located.

Suggested stop-sized gate: build one encrypted household contract in browser; persist/restart; issue and revoke expiring invite; remove an offline editor and rotate keys; resync remaining member after being absent; prove server has no decrypt keys; import same package in Expo dev build. Only proceed if source/behavior make access boundaries convincing. Do not develop full app screens first.

## HHSv3: real causal database/access option, separate confidentiality question

Current v3 is **not** `hyperhyperspace-core` v2. Primary current repo `hyperhyperspace/hhs3-ts`, pin `f550595fe02ae7853ea02ce7e4cde1eba8e0e907`: https://github.com/hyperhyperspace/hhs3-ts/tree/f550595fe02ae7853ea02ce7e4cde1eba8e0e907 .

README and implemented modules describe DAG log storage, MVT standard types, replication/sync/mesh, SQLite and IndexedDB stores, bidirectional relational projections, browser-safe host and browser client. This is substantially more than roadmap-only evidence. README marks monorepo WIP and module packages are0.1.0; do not invent production support commitments.

`RCap` manages named capabilities, `managedBy` delegation, identities and revocation barriers. Permissioned `RSet` validates signed operations against referenced capability versions and re-evaluates concurrent operations at later observed frontiers. Tests explicitly cover sequential revocation retaining legitimate earlier adds, concurrent revoke invalidating concurrent grants/uses, transitive delegation and cross-object ref-advance attacks. **Creators currently irrevocably hold every capability**; this is an explicit limitation for owner transfer/lost-owner removal.

Source: https://github.com/hyperhyperspace/hhs3-ts/blob/f550595fe02ae7853ea02ce7e4cde1eba8e0e907/modules/std_types/README.md . Causal relational DB and projection are real options if replacing Automerge is worthwhile. Do not assume every SQL table automatically inherits the desired household access policy; prove one permissioned household model.

Mesh authenticates peers and derives encrypted per-connection session keys. Host `app.json.allow` restricts authorized sync peers and defaults to accepting every peer if absent. This can map households to separate hosts/databases/identities with an explicit allow policy, but **a permitted durable replica can see the data it replicates**. No existing encrypted-payload group epoch/key redistribution/recovery API was identified in reviewed host/replica/std-types docs. A trusted household always-on replica is a coherent alternative if that privacy tradeoff is acceptable. Blind hosted storage would still require a separate existing group encryption stack; avoid hiding that gap.

Sources: https://github.com/hyperhyperspace/hhs3-ts/blob/f550595fe02ae7853ea02ce7e4cde1eba8e0e907/modules/mesh/README.md and https://github.com/hyperhyperspace/hhs3-ts/blob/f550595fe02ae7853ea02ce7e4cde1eba8e0e907/modules/rhost/README.md .

Substantive progression: Oct12 internet tracker defaults/live tests; Oct13 unified mesh config; Oct14 browser host/tab client and cleanup; Oct14 tracker batching fixes. MIT license. Browser IDB/OPFS path implemented; native Expo SQLite and WebSocket/crypto adapters not qualified. Recovery is not demonstrated by key serialization/CLI alone. Non-overlapping devices need a reachable persistent authorized replica; a tracker only discovers peers and is not durable data storage.

Suggested small gate: SQLite/IDB two replicas, one household reader/editor/admin capability model, concurrent removal/edit test, process restart and absent-client bootstrap using durable replica. Mark separately whether acceptable trusted-replica model meets product privacy requirements.

## Peergos: existing cryptographic groups and a useful new Rust client

Reference Java client/server pin `587e27288f7f59cf664ff870ac135ba2f17e4fea`: https://github.com/Peergos/Peergos/tree/587e27288f7f59cf664ff870ac135ba2f17e4fea . Actual API `UserContext.java` exposes createGroup/addGroupMembers/removeGroupMember, shareReadAccess/shareWriteAccess and cryptographic unsharing. Removal rotates group-directory keys. **`revokeShared=false` prevents access to newly shared items but retains capabilities already obtained for older items.** `revokeShared=true` additionally rotates all previously shared item keys, at cost proportional to shared content. Write unsharing also rotates signers. Downloaded plaintext or old copied ciphertext/keys cannot be erased.

Source: https://github.com/Peergos/Peergos/blob/587e27288f7f59cf664ff870ac135ba2f17e4fea/src/peergos/shared/user/UserContext.java . This caveat is crucial for a shopping-list file repeatedly updated under one old capability; select the strong revoke mode and test future versions.

Current product promises expiry/password/use-limited writable secret links, private sharing and server migration/mirrors. Offline section specifically promises logging in and reading recent files offline, not arbitrary offline writes and merge. https://peergos.org/features and https://book.peergos.org/features/sharing.html . Durable data availability requires at least one storing home server; encrypted blobs are not a guarantee that a newly provisioned device has complete unuploaded local changes. Password+MFA restores access from remote persistent storage; lost passwords/unuploaded mutations require separately understood backup/recovery paths.

A new native Rust client is functional pre1.0, not a hypothetical future rewrite: pin `052c01862369abd0ae3b0d65099279c3a38d92ab`, https://github.com/Peergos/rust-peergos-client/tree/052c01862369abd0ae3b0d65099279c3a38d92ab . README claims real-server and Java interop testing; modules include crypto, signed CAS pointers, cryptree capabilities/sharing/revocation, resumable uploads and folder sync. Oct12 ports Java v1.38 groups/blocking/writer quotas, following Sept25 writable-link and sync fixes. This improves a possible native bridge route, but no Expo/UniFFI/browser-WASM binding was verified. Reference browser is Java cross-compiled JS with its own environment; treating it as a small React SDK is misleading.

Automerge immutable-change files in a shared household directory could use existing encrypted storage/key lifecycle. Concurrent writes to one mutable snapshot file would need explicit CAS/conflict handling. Account-owner versus joint admin delegation and multiple independent household directories need qualification. Audits2019/2024 exist in repo; they do not cover the new Rust implementation or newest features by implication. Reference/Rust AGPL-3.0; web-ui GPL-3.0. Strong secondary candidate if a heavier native/storage adapter is acceptable.

## Other candidates, with concrete gaps

**CoMapeo/Awana.** Awana is the organization/platform context, not proof of an independent generic SDK. CoMapeo core pin `748ebc9e2b0fb3cbed6af22b9397e7f291b6be58`, native module pin `21af38b9d5c3c06d45e3f900a67c002d3e15ec53`. Real Expo56 plugin runs embedded nodejs-mobile backend, not pure Hermes core; activity Oct13. https://github.com/digidem/comapeo-core-react-native/blob/21af38b9d5c3c06d45e3f900a67c002d3e15ec53/README.md . Roles distinguish creator/coordinator/member/blocked, members can write own records but not others. That differs from collaboratively checking a shared list. **Official archive provisioning uploads every project encryption key to the archive peer.** https://github.com/digidem/comapeo-core/blob/748ebc9e2b0fb3cbed6af22b9397e7f291b6be58/src/member-api.js (`#addServerToProject`). Thus its existing durable remote route is a trusted data peer, not blind storage. Local leaving deletes keys on the cooperative device; reviewed source did not establish cryptographic future exclusion against a malicious formerly invited device retaining all namespace keys. Core MIT. Product-specific data/schema and static PWA gaps make transplant more extensive than a small feasibility spike.

**GUN/SEA.** Current commit `56278eb4a37c0b2ad543e15678fc39d2eeb974a2`, substantive radix fix Oct15, bounded SEA auth retry Sept16. Browser/RN examples, AsyncStorage adapter and WebView crypto examples exist. `SEA.certify` explicitly warns early experimental community method; supports path-scoped delegated writes, expiry and graph blocklist. `sea/index.js` checks blocks and expiry; causal concurrent revocation semantics are not documented as equivalent to HHS RCap. `sea/share.js` establishes pairwise shared secrets, and `.secret` warns API may disappear. No complete household epoch rotation/recovery system proved. https://github.com/amark/gun/blob/56278eb4a37c0b2ad543e15678fc39d2eeb974a2/sea/certify.js and https://github.com/amark/gun/blob/56278eb4a37c0b2ad543e15678fc39d2eeb974a2/sea/share.js . Signed decentralized graph != encrypted group lifecycle. Durable relay configuration/retention and meaningful write acknowledgement need qualification. MIT/Apache dual license in LICENSE.md. More app crypto/key-policy burden than Chelonia.

**Holochain.** Active engine `2aad34f469f73a949d2b9ce8fa097172aceeee28`, Oct14 data cleanup and DHT read performance work. Real offline source chains and deterministic shared validation, no global chain consensus. https://developer.holochain.org/build/capabilities/ governs **zome function calls**; revocable grants are not automatically group decryption keys or removal from replicated DHT. Private entries remain source-chain-local; public DHT entries are not made confidential by encrypted network links. Existing Android conductor service/FFI/Tauri route pin `a7b5bb12a64d837694a6939701823d61803654bf`: https://github.com/holochain/android-service-runtime/tree/a7b5bb12a64d837694a6939701823d61803654bf . Browser extension conductor pin `0c391226e78769d44ccb4661881ed8998b15f903` is genuine alpha development, with local IndexedDB keys and remote linker, zero-arc/no gossip: https://github.com/Holo-Host/holo-web-conductor/tree/0c391226e78769d44ccb4661881ed8998b15f903 . Extension requirement and Expo bridge are substantial UX/runtime adoption choices. Group encrypted DB keys/recovery and durable offline recipient bootstrap still need chosen application protocol. CAL-1.0 licensing. Do not reject it merely as alpha, but larger migration and security work currently exceed smaller candidates.

**Willow/Iroh.** Pin `d55d8f495a3558697983ecafa1e82eda22d9616f`, https://github.com/n0-computer/iroh-willow/tree/d55d8f495a3558697983ecafa1e82eda22d9616f implements Meadowcap and confidential sync over Iroh, and `src/store/persistent.rs` actually contains redb persistent storage. Prior broad statements that persistence is future work for every Willow implementation were inaccurate. Scope/path/read/write delegation is excellent for household-selected records, but read capability confidentiality during reconciliation, encrypted transport and encryption of payload at an authorized storage peer are distinct. Member future-key exclusion/recovery/identity-device UX not established. Rust-to-browser/Expo bindings are not qualified. MIT/Apache dual. Last repo push Aug31; do not infer transport's recent Iroh releases prove this extension tracks them.

**Verida.** `verida/verida-js` last push Apr15,2025, ISC. Approved-user database API requires caller encryptionKey for nonowner access; `updateUsers` changes permissions without rotating that existing key. Primary paths: https://github.com/verida/verida-js/blob/main/packages/client-ts/src/context/engines/verida/database/engine.ts and https://github.com/verida/verida-js/blob/main/packages/client-ts/src/context/engines/verida/database/db-encrypted.ts . This is narrowly an API observation, not a claim that no higher layer could ever rotate keys. React Native guide exists, but SDK activity and absent ready group lifecycle make it a weaker present fit.

## Minimum adoption invariants regardless of stack

One person belongs to several independently authorized households; local personal recipe archive is a different audience. Selected recipes are explicit destination copies. Household admin transfer/lost owner cannot depend on unrevocable creation authority unless the limitation is accepted. Reader/editor distinction must hold against a modified client. Removal must separate legitimate past access from future-key access, reject/recover stale writes predictably, and not silently lose unsynced edits. Recovery needs identity/key material **and** retained data/outbox, with no server plaintext exposure unless trusted-server mode is explicitly selected. Durable non-overlapping delivery needs an always-on replica/storage provider; trackers/gossip alone do not provide it.

For trial order in this lane: **Chelonia encrypted household contract first; HHSv3 causal ACL/database second**. Peergos is the next credible existing cryptographic storage lifecycle if those trials reveal serious gaps. This corrects earlier exclusions without claiming all integration gaps are solved.
