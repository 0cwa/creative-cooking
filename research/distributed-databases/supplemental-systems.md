# Additional database and policy systems

Reviewed 15 October 2026. These are primary-source screening findings, not executed Creative Cooking runtime qualification. Detailed integrated-library reviews appear in the other research lanes.

## Tachyon and Matrix

The user's [Tachyon archive](https://github.com/0cwa/tachyon/tree/ebc0e03c26fbd9bb4f3fda3a3aa698e1f2711bc0) contains reverse engineering and synthetic experiments of Aurora's experimental client-authoritative room DAG and DMLS epoch DAG over Matrix to-device delivery. It is not a source-reproducible reusable database library. Two synthetic peers exchanged encrypted messages and a removal experiment rejected the removed peer's subsequent normal send; arbitrary membership forks, live federation, crash consistency and new-device recovery remain unqualified. The [comparison chapter](https://github.com/0cwa/tachyon/blob/ebc0e03c26fbd9bb4f3fda3a3aa698e1f2711bc0/docs/chapters/08-comparison-roadmap.html) explicitly distinguishes this architecture from ordinary server-authorized Matrix rooms. Native Matrix SDK methods do not establish availability of the custom DMLS fork.

Matrix can carry arbitrary encrypted application events, so calling it a chat protocol does not make the composition technically invalid. It supplies messaging, accounts, devices and key infrastructure, however, rather than the local database, queries, CRDT merge, compaction or durable application outbox. Creative Cooking would own the adapter and reconcile two lifecycles. The previous Matrix-first recommendation overstated how small that integration would be. Keep it as a transport fallback, behind database-shaped contenders. No custom DMLS implementation is proposed.

## Existing access-control engines

There are good established options for permissions without inventing an ACL engine. They solve policy evaluation; content-key distribution is a separate responsibility.

| Layer | Existing options and source | How it would fit |
| --- | --- | --- |
| Relational server ACL | Postgres RLS/Supabase; database's normal transaction boundary | Household membership joins for download scope plus authorized uploads. Suitable default for a trusted Postgres stack. Use live membership, not only long-lived JWT household claims. |
| Relationship authorization | [OpenFGA parent/child and group roles](https://openfga.dev/docs/modeling/parent-child), [SpiceDB](https://authzed.com/docs/spicedb/concepts/consistency), [Ory Keto](https://github.com/ory/keto) | Model household membership, inherited recipe/list access and future explicit share groups. These add a server service and consistent tuple-update obligations. Probably unnecessary for initial three-role household model if database RLS suffices. |
| Embedded/general policy | [Cedar](https://docs.cedarpolicy.com/overview/terminology.html), [OPA](https://www.openpolicyagent.org/docs), [Apache Casbin](https://casbin.apache.org/docs/overview/) | Existing RBAC/ABAC policy evaluators can avoid handwritten generic authorization logic. App still supplies authenticated identities, authoritative facts and enforcement on every read/write path. A local cached permission decision is not cryptographic revocation. |
| Offline cryptographic authority | Keyhive, p2panda auth/spaces, Meadowcap, UCAN; detailed in other lanes | Verify authority at peers without relying only on a server. Encryption, causal removal policy, proof dissemination and recovery differ; do not substitute a certificate spec for an integrated library. |

SpiceDB's [consistency documentation](https://authzed.com/docs/spicedb/concepts/consistency) explains why stale relationship checks matter after revocation and provides ZedToken freshness controls. Introducing an authorization service does not automatically solve the transaction boundary between changed membership, payload writes and replicated snapshots. For small household scopes, the fewest independent authorities is a useful simplicity criterion.

## Boundaries that apply to every option

Offline shopping edits are a product requirement; offline administrator membership changes are a separate, stronger capability. Server-coordinated membership is an acceptable candidate to compare, not automatically a failed local-first design. Specify whether stale offline writes are accepted, rejected or quarantined after removal. Preserve old local work for explicit recovery without granting future publication rights.

The renewed review does not silently relax the earlier E2EE direction: trusted-server alternatives are conditional choices shown to the user, while host-blind options must demonstrate authenticated key distribution and future-key removal. None can withdraw plaintext already held by an authorized former member. Allergy profiles make that distinction worth deciding explicitly, without blocking generated-data feasibility work.
