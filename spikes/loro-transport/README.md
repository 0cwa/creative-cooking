# Direct transport spike

Serve this directory using `agent-heavy -- python3 -m http.server 18765 --bind 127.0.0.1`. Open two independent tabs, create an offer in one, paste it into the other and create an answer, then paste the answer back. Send fixture. The HTTP server serves static files only; it does not exchange signaling or object bytes. Signaling must travel out of band. `node --test spikes/loro-transport/transport.test.mjs` runs boundary tests.

C0 adaptation: the fixture reproduces `fixtureObject` exactly, but browser JavaScript cannot directly import its TypeScript source without a build. The JSON/base64 chunk format is spike-only, not an implementation of C0 ExchangeFrame or a frozen wire format. The sender observes an unauthenticated, in-memory receipt, which is neither C0 stored (durable) nor applied (imported). No encryption, signature, authority, object hash validation, or sync is implemented. Receiver staging is memory-only and lost on reload. A repeated immutable ID with different complete bytes is rejected while the receiver lives; K2 must verify actual object IDs and envelopes. The bundle currently shares the 16 KiB encoded frame limit, so it does not yet support every 1 MiB object accepted by chunking.

Native preparation: `native/` contains a standalone Expo development-build app and pinned dependencies; see its README. Native runtime and binary channel interoperability remain unverified. No native build or device operation was performed.

Browser observations on 2026-11-17: two T3 tabs in the same browser profile ran independent peers. Unmodified gathered SDP remained unconnected for at least 15 seconds, with local candidates but no successful candidate pair; this observation does not establish the cause. Replacing each mDNS candidate name with the machine's checked Wi-Fi IPv4 address before delivering that description produced a same-host UDP connection. This is an explicit environment-specific manual workaround, not proof of no multicast, LAN independence or cross-device connectivity. Any future pairing layer must authenticate the final descriptions after any such user-visible edits; never alter authenticated descriptions. No STUN, TURN, relay or signaling server was configured.

A second manually signaled connection used the same workaround. In the first connection `proof.sendResume([2,2])` sent the last chunk twice; the receiver reported pending index 2. Both peers were closed, new offers and answers exchanged, and `proof.sendResume([1,0])` completed the 20,000-byte object with checksum 2546416. The receiver remained alive in the same tab, so this is memory-only resume across channels, not reload or crash recovery. A received-in-memory acknowledgement came back. The backpressure test simulates bufferedAmount; actual congestion was not measured.

For a disk file roundtrip, `file-proof.cjs` clicks Export, saves the browser download to `T1_SCRATCH/downloaded.bundle`, and uploads that saved path into the import control. Set `T1_SCRATCH` and optionally `PLAYWRIGHT_MODULE` and `T1_BROWSER`, then run the script with the server running. `T1_CDP=http://127.0.0.1:PORT` connects to an already-running, task-owned Chromium-compatible browser; the caller owns and stops that browser.

On 2026-11-17 the proof passed using an isolated Brave Flatpak profile under `agent-heavy -- agent-headless`, with `--password-store=basic` and a local debugging port. The browser downloaded the file to disk and the import control read that saved file, logging `fixture-object` with bytes `[0,1,2,255]`. T3 preview did not report the download, and cached Chromium and Firefox executables failed with allocator errors on this host. The browser proof covers only this fixture and does not establish durable storage or cross-device transport.
