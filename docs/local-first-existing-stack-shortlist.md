# Existing stacks for household keys and transport

Research date: 12 October 2026. Related to #36, #48 and #49. **Prefer an existing encrypted collaboration stack before building our own group-key protocol or relay.** The previous ciphertext-mailbox proof remains useful boundary evidence; it is not the recommended production implementation.

Three independent research lanes screened [OpenHaven's 227-entry catalog](https://openhaven.net/api/protocols.json), then checked relevant projects against current primary documentation, source, package publications and releases. [OpenHaven's public JSON API](https://openhaven.net/developers/) enabled complete catalog screening. Directory metadata is discovery evidence, not a security audit or current SDK qualification. Adjacent relevant projects absent from the named catalog rows, including Jazz, were investigated explicitly.

## Recommendation

**First trial: Automerge + Matrix's existing encrypted-room infrastructure and SDKs. Challenger: Jazz Classic as a complete-stack replacement.** This reopens the complete-stack comparison without discarding the completed local household work or migrating production data.

Matrix best preserves the current Automerge choice while providing an existing key lifecycle, encrypted durable transport, membership, device verification and recovery ecosystem. Browser clients can use the maintained Matrix JS SDK; an existing React Native TurboModule over the Rust SDK removes the assumption that we must write that bridge ourselves. The remaining app work is a scoped Automerge-to-room adapter and household UX, rather than a new encryption protocol or delivery server. This is a source-based recommendation for a bounded trial, **not app-runtime qualification**. [Matrix JS SDK](https://github.com/matrix-org/matrix-js-sdk), [React Native SDK](https://github.com/unomed-dev/react-native-matrix-sdk/releases/tag/0.10.2).

Jazz Classic is potentially simpler if we are willing to replace Automerge: encrypted group-owned data, permissions, native Expo integration and sync are already integrated. Its value is eliminating multiple app-owned boundaries. Using Jazz merely to transport Automerge creates two replicated data layers and is unlikely to deliver that simplicity. Classic's invitation limitations and transition to a different alpha architecture need explicit qualification. [Classic Expo documentation](https://classic.jazz.tools/docs/react-native-expo), [sharing policy](https://classic.jazz.tools/docs/react-native-expo/permissions-and-sharing/sharing).

Neither supplies the cooking product for us. App adapters are expected; cryptographic group protocols should remain upstream-owned.

### Matrix details that change the assessment

- The maintained core SDK releases reviewed are JS **43.0.0** and Rust **0.19.1**. The existing third-party native package **@unomed/react-native-matrix-sdk 0.10.2**, released 30 September, pins Rust SDK **0.18.0**. It is Apache-2.0 and built with UniFFI/TurboModule tooling. Its development RN version is **0.76.9**, so do not assume compatibility with our **0.86.3**. [Native release](https://github.com/unomed-dev/react-native-matrix-sdk/releases/tag/0.10.2), [pinned Rust configuration](https://github.com/unomed-dev/react-native-matrix-sdk/blob/0.10.2/ubrn.yaml).
- Generated APIs expose room invitations, kick/ban, power levels, encrypted raw-event send, SQLite/session restoration, device verification and backup/recovery. That is stronger than a protocol-only promise, but presence in source does not prove every flow in Expo. The bridge is a smaller third-party project and does not inherit the maintenance confidence of the whole Matrix ecosystem. [Generated API](https://github.com/unomed-dev/react-native-matrix-sdk/blob/fb1204910ac43de120955ea56a84a170db5d0ba1/src/generated/matrix_sdk_ffi.ts).
- Use encrypted room events for opaque Automerge changes. Prefer a dedicated application event type; qualify decrypted custom-event receive first. A normal encrypted message body can carry a bounded payload if the existing binding cannot expose arbitrary content. Enforce the protocol's **65,536-byte event limit** and qualify attachments/chunk framing for bootstrap. Native raw send lacks a caller-provided transaction ID, so the app needs durable outbox reconciliation and change-digest deduplication. [Client-server specification](https://spec.matrix.org/latest/client-server-api/).
- Matrix permissions are server-coordinated room authority. Local cooking needs no account, but optional sharing uses Matrix accounts and a homeserver, hosted or self-hosted. It does not provide direct serverless LAN synchronization or Keyhive-style causal offline ACL convergence. Unknown/new memberships must refresh before publishing; rejected removed-member edits stay local for explicit recovery.
- Device verification, key backup and member removal must use SDK capabilities and be tested with our UI. Key/session rotation protects subsequent communication once membership changes are processed; retained old plaintext and old keys remain accessible. Room metadata can be visible even with encrypted content. Do not transfer a cryptographic audit claim from a primitive to the native wrapper/application. [Matrix encryption and membership guide](https://matrix.org/docs/matrix-concepts/end-to-end-encryption/).

### Jazz details that prevent premature adoption

- Pin **Classic 0.20.19**, not whichever main-branch API happens to be current. The published package exposes `./expo` and `./react-native`, with SQLite and SecureStore adapters. Source implements read-key rotation when membership changes. [Published package metadata](https://registry.npmjs.org/jazz-tools), [Classic native crypto upgrade](https://classic.jazz.tools/docs/react-native-expo/upgrade/0-20-0).
- **Jazz 2 alpha is different.** Its current main README describes incomplete Expo persistent/device-supported runtimes. Classic capabilities must not be projected onto that release line. No long-term Classic maintenance guarantee was established. [Pinned main README](https://github.com/garden-co/jazz/blob/63adeca0c18ca204d86592dbcc11048ed0996eaf/README.md).
- Classic documentation says invite links neither expire nor support revocation. That matters for household removal. First test direct verified Account-ID grants or the documented admin-approved join flow; do not invent an invitation crypto wrapper to conceal this limitation. No prior Jazz security failure is claimed here: the documented limitation is the evidence, and its exact consequences still need executable tests. [Invitations and approved requests](https://classic.jazz.tools/docs/react-native-expo/permissions-and-sharing/sharing).
- A matching Classic sync server can persist data for clients whose uptime does not overlap. Its documented self-host path uses persistent SQLite; confirm exact pinned server/client compatibility and restart behavior. The protocol is described as novel; no independent protocol audit was verified in this research. Reviewed cryptographic primitives do not settle that question. [Sync/storage](https://classic.jazz.tools/docs/react/core-concepts/sync-and-storage), [encryption](https://classic.jazz.tools/docs/react/reference/encryption).
- Replacing the engine must preserve our domain IDs, selected copies, original disagreements and portable backups. The existing explicit baseline/epoch migration work remains useful; it does not convert Automerge operation history into Jazz history. Test app-relevant conflict behavior before deciding that integrated SDK convenience outweighs migration.

## Bounded next bake-off

Start with Matrix's existing web and native SDKs. Keep Jazz Classic as the integrated challenger if Matrix requires excessive app-owned integration. Use synthetic cooking data and temporary local infrastructure; no production migration or public deployment.

1. **Fail-fast API/runtime gate:** exact pinned packages initialize in the static PWA and Expo57/RN0.86. Native send/receive, persistence and verification/recovery methods must work. Stop if success requires building a new SDK or rewriting its key protocol.
2. **Two households, two clients, one late reader:** genuinely encrypted shopping changes and one selected recipe copy, duplicate/out-of-order import, sender disconnect, relay restart, late catch-up and local application restart. Preserve source/copy isolation and original 4/6 then causal 5 evidence.
3. **Permissions and removal:** reader cannot publish standard or custom payload events; outsider/cross-household access denied; admin changes authenticated; removed offline device cannot publish or obtain future keys after membership refresh. Past access is explicitly distinct. Test stale/public/nonrevocable invite behavior for Jazz.
4. **Recovery and ownership:** enroll a replacement device using an existing verification/recovery mechanism, restore encrypted history, keep SDK secrets out of ordinary backups/documents, and enumerate hosting/upgrade/backup responsibilities.
5. **Decision:** compare application-owned code, native maintenance, required accounts/servers, confidentiality and merge semantics. Select a stack only from those executed results. If Matrix is viable, retain Automerge; if Jazz materially reduces ownership and passes the same gates, reopen the engine choice rather than preserve sunk work.

The [evidence inventory](../research/openhaven/evidence.json) records catalog screening, primary URLs and pins. These are researched capabilities and limitations, not executed household runtime results. No application dependency, key protocol, network service or production state changed in this survey.
