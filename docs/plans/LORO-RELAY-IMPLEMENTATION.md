# Loro household relay implementation plan

The [2026-11-17 interview decisions](LORO-IMPLEMENTATION-DECISIONS.md) are confirmed. This revision incorporates them; [policy contracts](LORO-POLICY-CONTRACTS.md) and [sync protocol contracts](LORO-SYNC-PROTOCOL.md) define the corresponding records and checks.

Status: revised implementation design, 2026-11-17, following confirmed product decisions. The current work revises documents and isolated models, not the production application or deployment. The PowerSync implementation remains on main and is archived at `origin/archive/powersync-2026-11-15`, commit `069d9abb10dd07bbde1ef13f69ae164f9a7d0143`. The planning root is `docs/loro-relay-plan`. There is no existing-data migration or dual write in scope. Eventual release must offer a clear fresh-start boundary and leave existing stored data intact until the user chooses; never silently reset or reinterpret it.

See the [execution plan](LORO-EXECUTION-PLAN.md) for package ownership, dependencies and integration gates.

## Decision and evidence

A household-first product: local-first Loro documents, equal adults, private personal data, visible trust branches, direct exchange, encrypted transfer files and an optional small encrypted HTTP mailbox. Routine edits are immediate and need no vote. Personal code recovery is independent; restoring current household authority requires separate admission evidence and current-adult confirmation. Guardian assistance is optional for the person but included in the first implementation, with explicit scope and thresholds. Adult admission defaults to all existing adults minus one, clamped to at least one; the two-adult consequence is deliberately accepted. A device vote is never an adult vote. Neither a majority nor a minority establishes truth.

| Choice | Default recommendation | Alternative and cost |
|---|---|---|
| Household membership | Adult admission needs `max(1, N - 1)` approvals from the frozen existing roster; concurrent successors remain visible | Unanimity or validated fixed adult quorum; current-state disclosure is explicitly delegated when accepting the admission agreement |
| Recovery | Personal code; household re-enrollment separately confirmed by a current adult | Configurable `t-of-n` independent guardians for a scoped package; withholding can block recovery; no automatic downgrade |
| Personal recovery | Independent code; setup may be deferred with a dismissible reminder | Explicit personal guardian package excludes household keys without a separate shared grant; threshold holders can read the package |
| Dispute | Keep branches and exportable local work; explicit content copy | Choose a known checkpoint and create a clean branch by explicit social choice; no mechanical claim that the choice is correct |
| Transport | Direct foreground exchange plus encrypted file alternative; no account or relay required | Optional relay enables delivery when peers do not overlap; background delivery is not guaranteed |
| Shared cooking AI | Minimize names/context; allow genuinely on-device processing; review exact external payload | Default external-processing preferences allow a recorded explicit override; advanced blocking rules remain blocking; no override for others' private content or key release |

Presets are finite and versioned, with fixed electorates and thresholds in each parent trust state. Advanced choices remain available through compatibility checks, not arbitrary scripts. There is no automatic threshold shrink or “all reachable” quorum. Membership counts people, not keys. Invitations and removals use the same counting semantics; warn that accepting additional identities changes future electorates. Policy changes themselves follow the existing preset; display the old and new rules, require the prescribed approval, and rotate affected keys. Existing members may fork instead of accepting a change. Accepted adult admission delegates only current cooking-state access, not deleted content, old activity, personal history or new providers. Current-state-only onboarding requires fresh projections and keys as specified below.

The [isolated experiment](../../spikes/relay-household-poc/README.md) uses a fixed scenario. Actual Loro 1.17.1 assertions show reordered and duplicate delivery converges, two distinct purchase IDs survive, independent recipe fields survive, and a disk snapshot reopens. Concurrent titles produce one current winner; the experiment reports both intentions and the superseded value, not preservation of both current values. The recovery/trust transitions are abstract: 2-of-3 guardians succeed with one unavailable and fail with two or one unavailable plus one withholding; multiple copies held by Ana count once. Two disjoint pairs of four can each approve a successor. Reordered delivery exposes both heads and does not settle authority. V5 models one rogue device and then two compromised devices owned by one adult: two device votes can approve while one of two adult votes cannot; a different adult explicitly chooses a minority checkpoint and benign operations. The clean Loro document is rebuilt from that choice; rejected operations remain exportable. The experiment does not establish which party is honest, real cryptographic security, crash-atomicity, or behavioral probabilities. Shopping comparisons are illustrative; physical purchases are not prevented by CRDT deduplication.

Sources and roles: Fable supplied the bounded [scenario](../../spikes/relay-household-poc/SCENARIO.md); Luna supplied household/crypto research; Sol assessed recovery and key separation; Sonnet proposed the protocol sketch; Haiku walked through UI and abuse cases; Opus assessed incentives; Terra implemented the PoC and this synthesis. All requested families participated; no Astra consultation. These are design inputs, not runtime proof. Sonnet's relay-order authorization, member-held seal/compact, all-reachable quorum and recovery-derived future identity are expressly rejected here. The [Loro sync documentation](https://loro.dev/docs/tutorial/sync), [encoding documentation](https://loro.dev/docs/tutorial/encoding), [Expo SecureStore](https://docs.expo.dev/versions/latest/sdk/securestore/), [Expo Crypto](https://docs.expo.dev/versions/latest/sdk/crypto/), and [RFC 9420](https://www.rfc-editor.org/rfc/rfc9420.html) provide primary context; none validates this application's security. See also [RFC 9591](https://www.rfc-editor.org/rfc/rfc9591.html) for the distinction between threshold signing and reconstructing a secret.

## Data and local transaction contract

Loro is the sole merge authority for shared content; the trust DAG is a separate authorization authority. Domain types remain authoritative for application semantics and versioned codecs validate data at the boundary. Use one document per recipe with stable ingredient and step IDs; one per shopping cycle/list with item needs and append-only purchase events; one per pantry item or bounded collection after measuring; and separate personal documents for chats and preferences. Provider API keys remain device-only in protected storage, excluded from all backups, recovery catalogs, guardian packages, documents and relay metadata. Chats and Chef proposals remain personal even when a household is selected; sharing selected content requires a deliberate copy into household scope with the audience shown. Meal context and settings use bounded documents with explicit scope. IDs are random stable identifiers, never display names or array positions.

A shopping need is distinct from a physical purchase. Each purchase gets a unique event ID, author and item reference; duplicate transport does not duplicate an event, while two adults buying one item remain two purchases. Corrections are compensating events referring to the original, not deletion. UI shows overbuy and lets an adult reconcile. Claims are advisory offline, not an exclusive lock. Define quantity units, cycle closure, deletion/tombstone and restore rules in codecs. For same-field recipe edits, retain an application intent record and surface the superseded value; do not promise that a plain Loro register retains every user intention in the materialized view. Ordered recipe steps need stable identity and explicit move/delete conflict tests.

Competing recipe intentions must be durably retained and discoverable, not merely logged if convenient. Before shipping, test conflict discovery across duplicate/reordered delivery, restart and generation changes. Excluded history is visible only to its authorized audience. External AI calls strip identity metadata by default and bind review to exact minimized bytes; preference overrides are recorded as disagreement, never group consent. A network model called local still has an external recipient. Provider endpoints and hidden prompt context cannot change after review without revalidation. Persist reviewed/sent/failed/unknown outcomes outside the Chef domain-effect transaction; a network disclosure cannot be rolled back by undoing its local record.

The local database is the durable transaction boundary. For each user command: validate scope and current accepted branch; compute semantic operations on a working document; persist resulting document snapshot or update, semantic intent, encrypted immutable envelope, and outbox row in **one** local transaction. Use the existing op-sqlite binding on native and a direct IndexedDB transaction spanning the required object stores on web, behind the same commit/reopen contract. UI says “Saved on this device” only after commit. Native and web adapters must demonstrate the same atomicity; if Loro's in-memory mutation succeeds but transaction fails, discard and reopen from durable state before accepting another command. Store ciphertext and nonce once; retries reuse identical bytes and content ID. Chef acceptance and its domain effects, including any purchase or recipe changes, commit in that same transaction with a unique effect ID so retry cannot apply them twice. External model calls happen outside the transaction and never imply a committed effect.

Inbound processing first persists ciphertext and its relay cursor in a transaction; fetched and applied cursors are separate. Authenticate envelope, validate branch, epoch, sender device and dependencies, import into a working document, and atomically persist applied state and outcome. Missing predecessors or document dependencies stay pending; invalid signatures, unauthorized or disputed-branch updates stay quarantined with raw export and reason. Never discard unsent local work because a branch changed or a process restarted. UI distinguishes local save, relay acknowledgement, peer receipt, pending and quarantine. A relay acknowledgement is not proof another adult received anything.

Suggested native tables and equivalent IndexedDB object stores: `documents(id,scope,branch,schema,snapshot,version)`, `intents(id,doc,author,semantic,provenance)`, `outbox(id,branch,epoch,envelope,status)`, `inbox(id,mailbox,cursor,envelope,status,reason)`, `trust_events(id,parent,body,signatures)`, `branch_heads(id,status)`, `checkpoints(id,branch,vector,hash,authorization)`, `device_receipts(device,head,cursor)` and protected key references. Add unique indexes on envelope IDs, semantic effect IDs and device counters. Encrypt sensitive local material according to platform capabilities; Database transactionality does not itself protect keys. Schema and envelope versions must reject unknown incompatible versions without dropping bytes.

## Identity, keys and recovery

A person is an adult identity with a stable public identity key and distinct device records; each device generates independent signing and encryption keys. Device signatures attribute changes but do not confer adult membership by themselves. Every household epoch and every personal dataset epoch receives a fresh independently random data key. Each authorized device receives an authenticated public-key envelope bound to household, epoch, recipient, algorithm and trust head. Personal keys are never in household envelopes. A personal recovery secret derives only a wrapping key for an authenticated key catalog; it never deterministically derives future data epochs or device identity. Use a reviewed, supported KDF, AEAD and signing/key-agreement binding only after exact runtime tests; secure randomness must fail closed. The PoC supplies no crypto proof.

The recovery kit contains a high-entropy secret, opaque backup locator, available custody locations (which may include a relay), catalog generation and hashes, and last trusted membership checkpoint. It must not require a relay address. Refresh the encrypted catalog and show backup acknowledgement whenever recoverable keys change. Anyone with an unchanged secret and future catalogs wrapped under it can read those catalogs. Compromise or guardian removal therefore requires fresh recovery material, fresh wrapping key, shares and continuity credential, and rotation of affected data keys; rewrapping the old credential is insufficient. Old plaintext and previously copied packages cannot be recalled. Rotation alone is not a forward-secrecy guarantee. Recovery setup is optional, with a dismissible reminder; show key recovery readiness separately from available data copies. Complete loss of copies is unrecoverable even with intact keys.

For personal code recovery, restore only the person's catalog and generate a new device identity; mark household membership unverified until a currently authorized adult confirms against a trusted checkpoint. A code is a bearer secret and can be lost or copied. Optional household guardian recovery reconstructs a separate continuity wrapping key with fixed independent people, not multiple devices of one person. It does not authorize ordinary edits or access personal keys. Optional personal guardians require explicit consent explaining that the threshold can read the protected personal package, excluding device-only provider credentials. Share integrity and authenticated reconstruction need audited implementation and tests. Withholding stays visible; never silently lower threshold. True threshold signing is out of scope.

Implement guardian assistance in the first release while leaving enrollment optional. Validate configurable `t-of-n` holder sets and display the access implied by `t = 1`. Personal packages exclude shared keys unless a separate shared agreement grants that guardian audience access. Household-assisted historical data recovery, personal restoration and current voting admission remain three different results.

## Trust, enrollment and dispute protocol

Trust events form a signed predecessor-linked DAG. A canonical encoded event contains `version`, `parent`, `kind`, `subjectPerson`, `subjectDevice`, `authorDevice`, frozen parent electorate and policy version, proposed membership/device changes, fresh epoch ID, key-envelope references, unique nonce and signatures. Event ID hashes canonical bytes. Verify signatures, adult/device mapping, parent policy, distinct eligible adult approvals and subject constraints before accepting a successor. An invitation binds an out-of-band fingerprint/QR, intended person identity, target device keys, parent head and expiration/nonce; both sides accept. An invite is a membership action. Adding or replacing a device attaches a fresh key to an existing adult and is not a new adult. Lost device revocation rotates affected keys and leaves membership intact. Adult removal retires all their device and recovery authorizations on the chosen branch and creates fresh epoch keys for remaining authorized devices. An adult's voluntary exit follows the same prospective rotation. Old plaintext remains readable to anyone who retained it.

One accepted device may pair another device of its own adult through explicit possession and transcript verification; no household-wide vote is needed and a visible device record is required. This intentionally accepts that a compromised accepted device may sponsor another device; quarantining/revoking only one device is not a guarantee that its adult identity is now clean. New-adult admission defaults to `max(1, N - 1)` under the parent roster and source delegation. Recovery-based device replacement cannot pretend to be surviving-device pairing.

New adults receive current recipe/pantry/shopping projections, not the old Loro snapshots or epoch keys. Create fresh document IDs/generations with independently keyed material, retain old archives for their old audience, and move accepting existing clients to the new generation. Rebase late semantic intents under the new policy; never import excluded historical operations as a shortcut. Preserve purchase/effect deduplication across this boundary without disclosing excluded payloads. Admission is not grandfathered permission to share somebody's private data. Canary tests must show that deleted content, undo records and pending imports do not leak in the serialized projection or its keys.

A proposal and approvals are immutable and independently attributable. Collapse equivalent open proposals by parent, action and subject in the UI, retaining all evidence and a repeat count. Rate-limit per device where relay attribution is available; do not pretend display dedup prevents quota flooding. Incompatible authorized successors are competing heads, never resolved by last-write-wins or relay sequence. A device records which heads it has seen. Show both membership sets, authors, approvals, unseen edits and local branch selection; keep both exportable. A device may continue local work on its selected branch without a quorum. Unseen or conflicting edits are pending/quarantined, not deleted. A late old-epoch edit is classified by signed causal/trust context and accepted branch policy, not by relay arrival order; if authorization is ambiguous, show it for explicit review rather than treating it as an attack.

Rejoin requires a fresh invitation under an authorized successor and acceptance by both parties. An adult may explicitly copy selected content across branches without merging membership; each copied semantic operation records its source branch and original ID. Do not import a tainted CRDT history merely to undo it. For destructive griefing, a user can explicitly choose an independently trusted checkpoint, select benign semantic operations, and rebuild a clean new document and trust branch; export the original history and rejected operations with provenance. Dependencies may make selective replay impossible or require manual reconstruction; never claim raw author operations can always be removed while retaining their causal dependents. Social trust in a checkpoint is user input, not a protocol oracle. Destructive undo or trust transition approval follows the configured preset and may fork; permission to make routine edits is separate.

Immediate local quarantine needs no quorum. A compromise report separately names the suspected boundary checkpoint or operation range and the prospective revocation. Another adult may accept a different boundary. Freeze available evidence into an immutable bounded review manifest; later source submissions cannot extend that review or generate repeated notifications. Inspect suspect-authored changes separately from honest dependent edits. Unknown/cyclic dependencies remain pending. Explicit fetch creates another review with a fresh budget, not an unlimited stream. Quarantine, transport buffers and relay verification queues each need separate limits; bound rejected summaries as well as valid input. A device cannot prove that it disclosed all its prior changes. Preserve disputed durable data rather than silently evicting it at capacity.

## Relay and checkpoints

The optional relay is a single-process HTTP service backed by SQLite and durable object storage on one host; start with filesystem objects and SQLite transactions where deployment supports durable fsync. No mandatory account service, Postgres, PowerSync, multicast or LAN discovery. HTTPS is required outside a trusted local development setup; discovery may later be an optional hint, never the source of authority. Direct WebRTC data channels with manually exchangeable signaling are the initial implementation target, plus encrypted bundle export/import. No external STUN/TURN or signaling service is required by the default contract. The transport spike must demonstrate browser/native direct exchange without a relay; do not silently ship relay-only sync if it fails. See the [transport bindings and primary sources](LORO-SYNC-PROTOCOL.md#pairing-and-direct-exchange).

A random mailbox ID and scoped bearer capabilities grant read or append. Store capability hashes server-side; never put names, provider keys or membership lists in relay metadata. Proposed endpoints: `PUT /v1/mailboxes/{mailbox}/objects/{contentHash}` for idempotent immutable upload, `GET .../objects/{contentHash}` for bytes, and `GET .../log?after=cursor&limit=N` for ordered pages with opaque IDs and a durable cursor. Bound payload, page size, request rate and quota; return explicit quota/full, expiry and retry responses. An acknowledgement means object and index were durably committed, not merely queued. Repeated PUT of identical bytes returns the same receipt; a hash mismatch fails. A lost acknowledgement is safely retried. TLS, bearer access and quotas limit abuse; they do not make the relay an authority or hide traffic size/timing.

Each encrypted envelope binds format, mailbox, document, branch/head, epoch, sender device, device sequence, nonce and payload kind as AEAD associated data; sign the canonical envelope to attribute an author even though members share an epoch key. Reject nonce reuse, malformed encodings and unsupported versions, preserve raw input for diagnosis, and apply limits before decrypting. Verify exact crypto libraries and encoding interoperability in implementation. Relay cursors are delivery hints only; no sequence can authorize an old epoch. On removal, create a new random epoch, mailbox and read/append capabilities and send them only in envelopes for remaining devices. Old capabilities may still work against the old mailbox, and a removed adult retains old content. No member-held seal or compact token: an adult must not be able to delete shared relay history by holding ordinary credentials. Operator-enforced retention/quota is explicit, not a trust decision.

A checkpoint is a full document snapshot plus schema, branch, epoch, content hash, covered Loro version vector and authenticated authorizations under the fixed parent policy. Clients independently validate authorization, envelope, hashes, schema and vector before importing; a relay's assertion is insufficient. Full historical checkpoints are for their authorized audience, not current-state-only newcomers. Start relay storage append-only with no member-triggered compaction. Publish configurable ordinary undo retention, quotas and explicit archive options; protect unresolved disputes, unsent work and the last required checkpoint from automatic cleanup. When full, stop acknowledging new uploads and show export/storage-pressure options. There is no unlimited no-loss promise. Before physical history pruning, require a grace period, verified checkpoint, documented recovery for long-offline peers, independent backups and explicit operator policy; never equate every member's acknowledgement with safe deletion or allow one member to force it. Test a stale device's unsent edits against the retained full snapshot; if dependencies are unavailable, preserve and offer semantic export rather than promise automatic merge. Provisional engineering budgets and review bounds are specified in the sync protocol, pending measurement.

A fresh bootstrap verifies the recovery kit's checkpoint against a trusted current adult or independently retained checkpoint. A relay can replay an internally valid old history or withhold a fork: signatures and a hash chain alone do not establish global freshness. Without a trusted comparison, display “freshness unverified,” retain local data and do not silently authorize a newer-looking branch. Compare peer heads on later contact; surface rollback, gaps or equivocation. Capability rotation and new envelopes limit future access only under the assumed crypto and honest device behavior.

## UI and implementation map

The household screen lists adults separately from their devices, with invitation, replace/revoke device and leave/remove as distinct actions. Show the selected policy and its consequences before changes. Recovery screens show code custody, backup acknowledgement, guardian holders and exact threshold, confirmation status and who can read an optional personal package. Never call a guardian share an ordinary device backup. A missing share is named without offering a silent downgrade. Fork screens name both heads, member sets, authors, approvals, and quarantined edits; actions are keep separate, export, inspect/copy, and mutually accepted rejoin. For clean reconstruction show checkpoint source, selected operations, excluded operations, dependence warnings and the new branch before approval. Do not describe a relay receipt as global sync.

Foreground exchange is the first-release promise; closing the app preserves pending work but promises no background delivery. Device addition and adult invitation are separate pairing actions, with no email requirement. Advanced settings include quorum, scoped guardians, disclosure enforcement, retention and compromise recovery in the initial release. Show exact minimized external AI payload and recipient; an accepted preference override is labelled disagreement, while a blocking rule offers permitted alternatives. A data-availability warning must remain distinct from a missing recovery-code reminder.

## Phases and acceptance gates

The expanded first-release scope includes advanced settings, direct exchange, newcomer confidentiality and compromise recovery. Earlier person-week estimates predated those requirements and are withdrawn; estimate after the runtime gates rather than implying that the original scope and cost are unchanged. Phases can overlap only where contracts are stable.

1. **Runtime and protocol gates:** pin schemas/encoding/suites and supported Expo/Hermes/Loro/native WebRTC versions. Validate secure randomness, key wrapping, guardian reconstruction and native/web transactions. Demonstrate browser-to-browser and browser-to-native direct exchange with the relay and external ICE services disabled, plus encrypted file exchange. Acceptance: tampered/replayed pairing fails; no key release before transcript verification; failed transaction never reports saved; unsafe algorithm fallback fails closed. Record exact versions and remaining platform limits. No production claim from a successful pure model.
2. **Local engine and domain:** implement codecs, recipe intention retention, shopping purchase events, transactional outbox/inbox, Chef idempotency, schema upgrades and encrypted export. Acceptance: offline edits, duplicate/reordered updates, distinct physical purchases, same-field alternatives, restart and crash injection at each commit boundary. Transfer the same authenticated objects through direct and file adapters. A run collecting zero tests is not success.
3. **Identity, admission and newcomer projections:** implement separate own-device pairing, adult admission, recovery admission, equal-adult mappings, versioned presets and visible signed DAG branches. Acceptance: threshold tables include one-of-two; device duplicates and newcomers cannot vote in the parent; a proposed rule cannot authorize itself; sibling successors remain visible. Newcomer serialized state and key sets must not reveal deleted text, history, private data or old pending imports. Existing offline work is rebased or preserved for review across fresh document generations; stable purchase/effect identities survive without history leakage.
4. **Optional relay and required recovery features:** implement the single-process service, durable receipts, quotas, code recovery, configurable scoped guardian packages and freshness checks. Assistance enrollment stays optional, but the implementation is not deferred beyond first release. Acceptance: no relay is required for local creation/pairing/direct/file use; dropped ack retry is idempotent; process restart preserves acknowledged objects; quota pressure is visible; code without data copy cannot claim recovery; old/withheld heads warn. Test varied `t-of-n`, duplicate holder copies, unavailability, withholding and guardian rotation. Private restoration never silently grants current authority.
5. **Disclosure, compromise recovery and hardening:** implement minimization, exact-payload review, recorded preference override, advanced blocking rules, retention controls, bounded intake, frozen review and clean reconstruction. Acceptance: name metadata is omitted; payload/recipient/purpose/policy changes invalidate review; local network inference is not treated as on-device; private/key release cannot use the override. Flooding cannot extend an open review, trigger endless notices, or silently delete protected work. Checkpoint selection is user judgment; dependent honest edits are labelled separately; unresolved dependencies survive restart/export. Review actual crypto/key lifecycle and recovery UI before release.
6. **Full-platform and release gate:** validate PWA/native app roots, supported browser pairings, Android ARM64 and iOS native/web exchange, relaunch, quotas, permissions, upgrades and recovery. Earlier isolated Loro x86 fixtures and PowerSync app-root tests are different evidence, not a Loro production app pass. Verify foreground receipts and truthful pending status with background delivery unavailable. All agreed advanced controls must be accessible; the fresh-start choice preserves existing data. Run adversarial review and restore drills, publish measured limits and host terms, then separately obtain production deployment authorization.

Budget hosting from measured encrypted object volume, egress, storage, backups and operator time; no credible monthly price follows from this PoC. A relay-free household has direct/file paths but no delivery guarantee if nobody can connect or transfer a file. Risks include compromised same-origin web code, lost recovery kits, shared-device compromise, malicious authorized edits, offline divergence, stale bootstrap, protected histories exhausting storage, backend operator loss, schema evolution and unsupported native bindings. Encrypting data does not hide timing or protect plaintext on a compromised device. Social trust and plaintext copying limits remain visible rather than being described as solved.

## Contract integration

The [bounded policy contracts](LORO-POLICY-CONTRACTS.md) and [sync protocol contracts](LORO-SYNC-PROTOCOL.md) define typed agreements, exact consent/override bindings, adult-counted quorums, explicit newcomer delegation, direct/file/relay parity and independent recovery outcomes. Defaults are not a global security ranking. Blocking rules and protected consents are distinct from overridable cooking-AI preferences. Unknown or conflicting authority remains pending; historical restrictions survive group changes outside the explicitly accepted current-state delegation. The original strict-policy model is retained; `agreed-contracts.mjs` adds decision examples for the newly agreed behavior. These models supply no runtime authorization, cryptographic proof or atomic-storage evidence.
