# Household replication feasibility slice

This isolated package runs the actual Automerge 3.5.0 engine. It is deliberately not imported by Expo: native engine qualification remains open. `npm ci && npm test` runs the contract, and `npm run evidence` writes machine-readable `artifacts/household-replication.json`. No transport or key stack is selected here.

The replaceable engine boundary is `repository({scope, actor, persistence, authority, publish, snapshot})`. It exposes serialized async `change` and `receive`, `projection`, `snapshot`, original `document`, and `allChanges`. `create/load/save` and `originalConflicts` are available for migration/inspection. `scalar(value)` uses Automerge RawString so competing scalar assignments retain their original alternatives rather than splicing names together. Callers must persist a unique per-device actor ID separately and supply it on reload; the repository retains it across isolated mutation/receive candidates. Reusing the same actor concurrently on different devices is invalid. The package uses raw Automerge changes, not Automerge Repo/SyncState or a wire protocol.

`scope` contains a household ID and immutable positive integer replication epoch. Each household has a separate document/storage key. Epoch changes require explicit new document creation/import outside this package; old-epoch changes are fenced. Document ACL is external: `authority.verify` must check authenticated sender, evidence, scope, epoch and action using trusted state. The test double proves the application boundary, not cryptographic authentication. Replicated `members`, credentials, API keys, tokens and private keys are excluded; actor IDs are not identities.

Shopping lists and items use stable-ID maps and separate monotonic tombstone maps. Removal hides a concurrent edit without destroying evidence. Restoring a removed item requires a new ID. Recipes are explicit independent copies of selected source recipes: only title, description, portions, ingredient name/amount and step text are copied; notes, shopping derivation, credentials, and requirements never hitchhike. Source updates do not silently change the copy. Ingredients and steps have stable IDs, ID orders, and tombstones. Move plus concurrent edit retains the edited entity; projection collapses concurrent move duplicate IDs. Fully concurrent moves still need product conflict/reorder policy.

Household requirements are an allergy-label map and diet enum (`none/vegetarian/vegan`). They are planning constraints, not a claim of medical safety. A future application must validate source ingredient information and display uncertainty. Cross-household recipe copies deliberately do not disclose requirements. A truly jointly editable shopping list should receive its own collaboration space/ACL rather than replicate a whole household document into another household; that transport/security model remains undecided.

Incoming envelopes are bounded and checked for space, epoch, schema, authenticated external authority, forbidden operation keys (including causally pending changes), forbidden hidden conflicts, immutable namespace changes, and full resulting document schema. Invalid candidates are isolated with `clone`, rejected, and recorded in metadata-only quarantine. Structural ID conflicts are quarantined for explicit resolution; original scalar alternatives remain available. This is bounded ingress protection, not a formally audited hostile-wire parser. Trusted authority implementation must verify each change author/credential lineage as required by the eventual stack; an authenticated relay alone is insufficient for malicious clients.

Persistence must finish before state installation/publication. `memoryPersistence` is a reference test adapter. `indexedDBPersistence` is a browser adapter resolving only when its read/write transaction completes. Its connection/restart contract is tested with fake-indexeddb; actual browser crash/process-restart qualification remains open. Publication failure leaves the change durable and available through `allChanges`; production needs a transactional durable outbox and acknowledgement/retry contract. No transport success implies convergence or delivery completion.

## Application mapping

The local domain agent's `HouseholdWorkspace` uses `id/name`, `shoppingList` arrays, `recipes` copies and `requirements` arrays. At the engine boundary map workspace `id` to `householdId`, one local shopping list to `shoppingLists.default`, and item `id/name/amount/checked` to its stable-ID map entry. Preserve local personal `pantryPreference`, timestamps and unrelated recipe fields in personal storage. Allocate recipe ingredient/step stable IDs once when explicitly sharing a copy; the copy keeps sourceRecipeId only for provenance. `workspace-adapter.mjs` implements the normalized array mapping as a one-time `bootstrapWorkspace(repo, workspace, credentials)` into an empty document. It returns an explicit household/epoch local sidecar for timestamps, workspace name, source recipe identity, and pantry preference; this sidecar is never replicated. `exportWorkspace(doc, {sidecar, targetHouseholdId, replicationEpoch, now})` creates the corresponding safe household array view and checks scope. It rejects repeated bootstrap, cross-household/epoch exports, and flattening multiple engine lists. Legacy array exports omit engine step/ingredient IDs: the Automerge snapshot remains the lossless backup. This closes baseline snapshot mapping; live app-to-engine command integration remains a gate.

## Proven and remaining

Tests cover household isolation, authority denial, epoch fencing, offline add/check merge, duplicates, out-of-order dependencies 4/6 then 5, pending snapshot/restart, remove/edit nonresurrection, original scalar alternatives, stable actor/sequence after receive and restart, safe one-time workspace bootstrap/export, independent safe recipe copies, ordered move/edit, persistence failure, transaction-complete IndexedDB restart, hostile ingress and async mutation serialization. Remaining before production: native Android/iOS execution, browser actual crash lifecycle, live app-domain command integration, full key/ACL/revocation design, encrypted relay/transport qualification, durable publication outbox, quotas/compaction, and malicious-client audit.
