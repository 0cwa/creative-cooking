# Candidate crypto experiment

This is not C1, a production provider, a durable key store, or a security approval. `test-provider.mjs` deliberately keeps test secrets in an in-memory map and uses libsodium-wrappers 0.7.15. The caller must provide real key storage, key authorization and provider error handling. The fixture identity seeds are public. Never use them for user data. Hermes RNG and native exchange remain unproved.

For an isolated run, copy `src/loro/crypto` and `src/loro/pairing/candidate.mjs` into the same paths under a scratch directory, install `libsodium-wrappers@0.7.15` and `esbuild@0.25.12` there, then run `agent-heavy -- node --test src/loro/crypto/candidate.test.mjs`. For browser exchange, bundle `src/loro/crypto/browser-fixture.mjs` with esbuild, serve an HTML page loading that bundle, and run `agent-heavy -- node src/loro/crypto/node-fixture.mjs generate`. In an isolated browser, await `window.ready`, fetch `packet.json` and call `window.exchange.open(packet)`; call `window.exchange.generate('fresh browser to Node')`, save its result as `browser-packet.json`, then run `agent-heavy -- node src/loro/crypto/node-fixture.mjs open`. Each direction generates a fresh data key, sealed key packet, nonce and content ciphertext. Output is test ciphertext only; never log key material.
