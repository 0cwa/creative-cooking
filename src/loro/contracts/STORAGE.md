# Storage contract C0.1

C0.1 changes storage only; Transport and ExchangeFrame remain unchanged. S1 fixtures model older shapes, and S2 adapters, L1 runtime and domain/Chef consumers must adopt this contract before integration. This contract does not select a cryptographic suite or establish native runtime proof.

All identities are scoped by `scopeId` and by their namespace (operation, command, effect, document, object, inbox item and receipt). The local command array is one operation/effect group, identified by operationId; command and effect IDs are individually unique. `storageOperationKey` defines exact equality for the complete input, including expected revisions, byte contents, associations and ordered arrays; it is an internal comparison representation, not a wire format or hash. Persist the complete representation or an equivalently collision-free comparison, not an unverified hash alone. Local and import operation namespaces are distinct. Inputs must pass validation before any write. Documents are ordered strictly by documentId and unique; other arrays retain order and IDs within each namespace are unique. Bounds are provisional, per operation; excessive byte or item counts return TOO_LARGE, malformed shapes return MALFORMED.

In one database transaction, first look up the scoped operation identity. If a completed operation exists, compare its entire input; exact equality returns the original saved revisions with replayed=true, even if the expected revisions are now stale. Otherwise conflicting identity reuse returns CONFLICT with zero writes. An incomplete or partial pre-existing set of operation, command, effect or object identities is a conflict, never a successful replay. Any reused identity with different bytes or associations is a conflict. For a new operation compare all expected revisions in the same transaction as all writes. Null requires absence and creates revision 0; an existing matching revision increments by one. A revision at MAX_SAFE_INTEGER cannot be updated. Any mismatch or failure leaves all documents, effects, immutable objects, outbox and operation record unchanged; caller reloads durable state. Cross-tab/process exclusion must come from database transactions, not an in-process mutex. Authority is revalidated by the caller before every invocation, including retries.

Stage inbox object bytes and cursor in one transaction. Cursor comparison is exact string equality, with null meaning absent; cursors are opaque and never ordered. Existing identical staged bytes may be reused, but differing bytes for the same scoped object ID conflict. A failed cursor comparison makes no writes. Import refers to an existing staged item, atomically writes all documents, effect IDs and its applied outcome, and preserves staged bytes on failure and success. Import replay follows the same complete-operation rules; an item already applied by a different operation conflicts. Storage does not verify authenticity.

Outbox entries and immutable effect/operation history survive receipt recording. Record receipt identities idempotently with exact field and byte equality; conflicting reuse writes nothing. Track each destination and recipient independently. Relay stored and peer stored/applied are distinct; peer applied requires a prior peer stored receipt for that object and recipient, and no transition regresses. A receipt is untrusted until verified by a higher layer. Receipt persistence never authenticates it, deletes an outbox entry, or implies delivery to another recipient. Queue selection may use these persisted states; deletion/retention policy is outside this contract.

Pure validators return typed errors and never create `Verified` values. Contract tests establish shape and equality only: database atomicity, crash recovery, quota mapping and concurrency require real adapter tests.

## Atomic local group

`commitLocalGroup` accepts a `LocalCommitGroup` with a local `groupId` and ordered scoped `LocalCommit` children. It is additive to `commitLocal`. Group identity is local to this database and separate from every scoped operation namespace. Authorize every child scope before every call, including replay. The group does not grant access, release keys, combine ciphertext or create a distributed transaction; each child's document, command, outbound bytes, scope and audience stay separate. Chef proposal status in a personal child and its household domain effect in another child commit together locally.

Validate every child and aggregate counts and actual bytes before writing, using `storageGroupKey`. Group limits use the existing operation budgets across all children and at most 16 children. Within one scope, duplicate operation, document, command, effect or object identities across children are malformed; identical IDs in different scopes are distinct. Child order and each complete child input are part of group equality. Store the full group comparison key and ordered child outcomes. In one database transaction, look up the local group identity first: an exact completed group returns the original ordered outcomes with replayed=true before checking stale revisions; a changed group under that ID conflicts. If no completed matching group exists, any pre-existing child operation, command, effect or outbound object identity conflicts, including children committed independently or from an incomplete group. Existing documents are checked by their expected revisions, not treated as partial child records. `classifyStorageGroup` expresses this decision from facts read in that transaction; it does not inspect a database or prove atomicity. A new group compares all child revisions and identities and writes every child and the completed group record in the same transaction, or writes nothing. Sequential calls to `commitLocal` cannot implement this guarantee. Receipt and import operations are not group children.

## Candidate pairing release boundary

`PairingAtomicStorage` is additive; existing single-scope and group commits and transport frames do not change. `CeremonyTranscript` carries both role-labeled device IDs and signing/wrapping public keys, distinct 32-byte nonces, complete ordered signaling bytes, session, exact action, personal or household scope, purpose, accepted parent and the identifier of the complete accepted authorization state. Invite-adult is household-only; the authority verifier decides all remaining action/scope eligibility, including same-adult sponsorship and recovery admission. Structural checks cannot establish randomness, completeness, identity, authorization or authentication. The verifier must authenticate independent out-of-band key pins, both role-specific signatures and wrapping-key possession over the exact ceremony bytes, authenticate the independent guard, and check authorization; a self-signature does not establish a human identity. A candidate verified result is not production approval. No suite or canonical wire encoding is selected here.

The guard ID is an independently generated, authenticated stable ceremony/session identity, not solely a transcript digest or caller-selected alternate encoding. Its authentication binds scope, direction and purpose. Guard IDs are unique database-wide, including across scopes and directions; operation IDs and packet IDs are scoped by scope kind and ID, in separate pairing operation and pairing packet namespaces. Implementations must prevent a guard from being reused with another scope or operation. The guard and transcript must match the authenticated verifier result byte-for-byte; storage does not itself authenticate a `Verified` value. Runtime integration must enforce the verifier boundary, including across serialization or process boundaries. Arrays retain order, bytes compare byte-for-byte, IDs compare exact JS strings without Unicode normalization, object property order is immaterial. `pairingReleaseKey` is a collision-free comparison representation of validated fields, not a signed encoding or hash. Persist the complete representation or equivalent exact fields. Limits apply to actual bytes and counts; validators return MALFORMED, UNSUPPORTED_VERSION or TOO_LARGE before writes. The caller must not mutate input or verified values during an asynchronous operation; implementations must snapshot them at entry.

The authority writer owns a durable scope-keyed `PairingAuthorityRecord` in the same database. It stores the complete accepted authority state as opaque `authorityState` bytes alongside its snapshot identifier and accepted parent, with a monotonic safe integer revision. The authority writer validates that the snapshot identifies those exact bytes; this record is the source of truth for pairing authority, not a cache of an independently writable record. `compareAndSwapPairingAuthority` compares the actual current record revision (null means absent), creates revision 0 or advances exactly one, and atomically writes the entire authoritative record. Any other records are derived from this record, or must be updated in the same database transaction by an adapter-specific extension. The present CAS writes this record alone; no extension is implemented. A standalone callback or comparing two caller-supplied revisions is insufficient. Consumers must not use a projection until authority validation has established its meaning. All writers that can change relevant authority must update this projection atomically. CAS conflicts and overflow write nothing. This boundary does not define governance decisions.

Before preparing randomized ciphertext, `findPairingRelease` checks for an existing operation. A found release must be checked against the current authenticated ceremony and reauthorized before transmission. If absent, prepare the exact recipient-encrypted packet; never persist plaintext key material in the release, outcome, guard, outbox or history. In one transaction, `commitPairingRelease` validates and snapshots input, the caller must first verify exact equality with its authenticated transcript and guard; storage then reads the complete operation and guard/object identity records. An exact completed operation returns its original packet and outcome with replayed=true before revision checks; changed operation reuse, guard reuse, packet identity reuse, or partial identity records conflict with zero writes. For a new operation, read the durable authority record and compare its actual revision, scope, parent and snapshot with the release. Mismatch, absent record, failure or duplicate identity writes nothing. Otherwise persist complete input equality, guard, exact packet, outcome and outbox atomically. Revalidate authority before every transmission, including replay; a stale replay is not permission to transmit. Scope, guard, recipient and purpose must also be cryptographically bound into the actual encrypted packet by the future codec.

`PairingRecipientStorage.installAndReceipt` is available only where a locally wrapped key record and authenticated acceptance receipt can be written in the same database transaction, backed by an available durable master key. The receipt must bind the exact accepted packet and ceremony and be authenticated by the recipient. Validate complete operation equality and reject identity reuse; persist the wrapped key record, receipt and operation outcome together or nothing. An OS keychain call cannot join an IndexedDB or op-sqlite transaction: if no such transactional wrapped-record implementation exists, return UNAVAILABLE without installing or issuing a receipt. The current `KeyStore` interface alone does not provide this capability. Real crash, concurrency, quota and master-key-loss tests are required for adapters.

Pairing, authority writer, storage adapters, recipient key storage, codecs and transport callers must adopt this boundary before durable release can ship. Existing candidate Node/browser key envelopes do not establish native Hermes RNG, secure persistence or production readiness. C1 encoding, algorithms, signature domains, independent review and native execution remain open.

At base `7c5df9a`, `TransactionalStorage.listRecords` exposes scoped document, object, inbox, cursor and receipt-state records for runtime queues. It does not expose authority or pairing-release records, and its separate read transaction cannot implement the commit-time authority or replay comparisons above. The typed authority and release lookup methods therefore remain separate; adapters may share internal read machinery while preserving the specified transaction boundaries.
