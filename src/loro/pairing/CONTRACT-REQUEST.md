# Candidate pairing contract request

Candidate only; this is not C1 or production security approval. `ceremonyBytes` binds session, exact action, personal or household scope, accepted parent, authorization snapshot identifier, role-labeled device IDs, signing and wrapping public keys, distinct fresh nonces, and the complete ordered signaling bytes. The snapshot identifier must identify the complete accepted authorization state. Verification requires independently authenticated out-of-band key pins, two role-specific signed confirmations, encrypted wrapping-key possession, authorization, and durable replay handling. Its result is not C0 `Verified` and cannot release keys. Confirmation and possession implementations must bind the exact ceremony bytes, and a self-signature is not human identity.

Before integration, the contract owner must specify a stable independent ceremony/session identity, canonical C1 encoding, scope and action rules, snapshot representation, confirmation and possession evidence, and typed errors. Replay identity must not be derived solely from a caller-supplied transcript digest or alternate encoding.

Pairing and storage need `commitPairingRelease`: prepare encrypted packet first, then atomically compare the ceremony guard and expected authority revision against the actual durable authority record, and persist guard, exact packet bytes, outcome and outbox. Identical retries return the original bytes; conflicting session reuse fails. Authority must be revalidated before each transmission. Pairing, authority, storage and transport consume this contract. Recipient key installation and receipt need one atomic durable transaction; if the key store and receipt store cannot provide it, installation must explicitly fail unavailable rather than split the operations. An OS keychain API alone does not establish that atomicity.

`candidate.mjs` is an isolated injectable experiment, not wired to the app or C0 interfaces. Its provider must implement all cryptographic and key-store operations; no provider or dependency is selected for production. Hermes secure RNG and native/web exchange, durable authority and replay, actual QR verification, and independent security review remain unproved.
