# Authority candidate

The authority chain validates signed policy changes against an explicitly preaccepted pinned root. It stores observed signed children and signed local branch selections in the existing authority record using CAS. A policy change is checked against its frozen parent, with distinct eligible adults and the parent policy's threshold. Concurrent children remain visible. Reads replay signatures and policy hashes from the pin. CAS conflicts require reloading and revalidation. Root provisioning and permission to bootstrap remain the caller's responsibility.

The verifier's provider must resolve each pinned `signingKeyRef` to the exact authenticated Ed25519 public key; changing the mapping invalidates the trust assumption. The root pin, hash and signature domains and JSON encoding are candidate formats, not C1. A production identity binding, enrollment ceremony, native crypto validation, replay/storage rollback protection and security review remain required. Hashes authenticate bytes only relative to a separately authenticated pin. The pinned root binds the document ID, generation, epoch, active device-to-Loro-peer mapping and permitted recipient devices. The runtime resolver replays the selected head and returns its durable revision and snapshot for storage CAS. The former preaccepted JSON behavior is restricted to `FixtureOfflineRuntime`; `OfflineRuntime` requires the pinned verifier. Changing the selected authority invalidates a runtime instance's old scope. No existing data is migrated.

Admission, own-device pairing, recovery, removal and revocation cannot be published by this candidate. Invitations return pending until admission, source delegation and fresh-projection evidence are verified; own-device pairing returns pending until the genuine ceremony, fresh key possession and transcript are verified. Local selection does not assert consensus or silently merge branches. The caller must authenticate and authorize any CAS writer. The signed selection requires an active device on the selected parent, but cannot itself establish human enrollment.

`resolveRuntimeAuthority(storage, scope, rootPin, provider, authorDevice)` reads and replays the durable authority record, derives runtime scope from the selected head and returns the corresponding revision precondition. Runtime inputs are compared to the derived values; they do not define author or recipient authority. A caller must pin and protect the provider's exact key mapping and root, and reauthorize at transmission. Sibling observations can advance the record revision without changing the selected head; a branch selection invalidates the old runtime scope.
