# Creative Cooking API foundation

This package implements account sessions and personal/household membership on PostgreSQL. It deliberately does not choose or implement the content replication engine. It creates no recipe, pantry, shopping, chat, sync, or provider-key rows.

## Run locally

Requirements: Node.js 22.13 or later, npm, and Docker or Podman Compose. Run these commands from `server/`:

```sh
npm run prepare:local
docker compose up -d --wait
npm ci
npm run db:migrate
npm run dev
```

`prepare:local` creates ignored `server/.env` with random credentials and mode `0600`, and never overwrites an existing file. The Postgres service uses the Docker Official Image `postgres:17.11-bookworm` pinned to index digest `sha256:858bb5e98eed02eb8cafbcdc007f9a65d1b613972028944a8ec2133ccaf80d27`, binds only to host loopback port `55439`, and uses a bounded 2 GiB temporary data filesystem, 2 CPU cores and 4 GiB memory. It creates separate `creative_cooking` and `creative_cooking_test` databases. Tests use only the latter, so they do not truncate local development data. `docker compose down` stops it; the database contents are intentionally ephemeral. Do not point this local Compose setup at production data.

The API listens on `http://127.0.0.1:8787`. `API_ORIGINS` must contain exact browser origins, comma-separated, for example `https://your-name.github.io` for a GitHub Pages PWA. Localhost origins are allowed for development. Origins absent from that list are rejected; requests without an `Origin` header are supported for native clients. CORS does not allow credentials or cookies.

## Session model and deployment limits

Register and login return a cryptographically random opaque bearer session token. The server stores only an HMAC-SHA-256 token hash, using required `SESSION_TOKEN_PEPPER`, and checks the live session on every authenticated request. A session expires after 30 days; `POST /v1/auth/refresh` rotates the token and starts a new 30-day window. Refreshing invalidates the old token. Logout revokes the current session immediately. Tokens are never placed in URLs, and authorization headers are redacted from request logs.

This bearer design works for native and cross-origin static web clients without third-party cookies. Native clients should keep the token in the platform secure store. A browser client should persist it in IndexedDB, not a URL or log; JavaScript executing on the Pages origin can still read it. Use HTTPS, a restrictive Content Security Policy, dependency controls and careful XSS prevention. CORS limits which browser origins can read API responses, but it does not protect a compromised allowed origin. No browser session storage is implemented in this server package.

Passwords are Argon2id-hashed. Request bodies are limited to 16 KiB. Registration and login allow 10 requests per minute per IP; all routes allow 120 per minute per IP, using an in-process store. Fastify does not trust forwarded IP headers. A production multi-instance deployment needs a shared rate-limit store and a correctly restricted trusted-proxy configuration. This package does not include email verification, SMTP delivery, password reset, OIDC, or account administration. Email addresses are not verified; invitation tokens are bearer credentials returned once to the owner for sharing through a trusted channel, and only their hash is stored.

There is no end-to-end encryption. This server can read account and membership metadata, and later server-side content tables will be visible to its operators unless a separate encryption design is added. The service never accepts or stores provider API keys. Do not expose Postgres directly to clients. Membership checks must remain in the request path for every content read/write, even if a later sync token contains cached scope; stale tokens do not grant membership.

## JSON API (`/v1`)

All requests and responses use JSON and camelCase field names. Authenticated requests use `Authorization: Bearer <sessionToken>`. Errors are `{ "error": { "code": "...", "message": "..." } }`. UUID identifiers are generated by PostgreSQL. Successful response shapes below are exact; timestamps are ISO-8601 UTC strings.

| Method and path | Authentication | Request | Success |
| --- | --- | --- | --- |
| `GET /health` | none | none | `{ "status": "ok" }` |
| `POST /auth/register` | none | `{ "email", "password" }` | `201` and `AuthResponse` |
| `POST /auth/login` | none | `{ "email", "password" }` | `AuthResponse` |
| `POST /auth/refresh` | current bearer | none | `{ "session": { "token", "expiresAt" } }`; rotates token |
| `POST /auth/logout` | current bearer | none | `{ "loggedOut": true }` |
| `GET /me` | current bearer | none | `{ "user": ApiUser, "spaces": ApiSpace[] }` |
| `POST /spaces` | current bearer | `{ "kind": "household", "name" }` | `201 { "space": ApiSpace }` |
| `GET /spaces/:spaceId` | current member | none | `{ "space": ApiSpace }` |
| `GET /spaces/:spaceId/members` | current member | none | `{ "members": SpaceMember[] }` |
| `POST /spaces/:spaceId/invitations` | household owner | `{ "email", "role"? }` | `201 { "invitation": SpaceInvitation & { "token" } }` |
| `GET /spaces/:spaceId/invitations` | household owner | none | `{ "invitations": SpaceInvitation[] }`; tokens are omitted |
| `POST /invitations/accept` | invited account | `{ "token" }` | `{ "space": ApiSpace }` |
| `DELETE /spaces/:spaceId/members/:userId` | household owner | none | `204`; removes membership only |
| `POST /spaces/:spaceId/leave` | current member | none | `204`; removes the caller's membership only |

`ApiUser` is `{ id, email }`. `ApiSpace` is `{ id, name, kind, role, createdAt }`, where `kind` is `personal | household` and `role` is `owner | editor | viewer`. `SpaceMember` is `{ user: ApiUser, role, joinedAt }`. `SpaceInvitation` without its one-time token is `{ id, email, role, expiresAt, createdAt }`.

Registration atomically creates one personal workspace with the registering account as owner. `POST /spaces` creates a household; personal workspaces cannot be invited to or left. Only an owner can invite or remove household members. Invitations last seven days, are bound to a normalized email, allow only `editor` or `viewer`, and can be accepted once. Concurrent acceptance is serialized in PostgreSQL. A last owner cannot leave or be removed. Removing a member deletes only the membership row; it preserves the member's personal data and household rows. Their still-valid account session cannot read or write a workspace after membership removal because authorization is queried from current membership on each request.

The exported `requireMembership(pool, userId, spaceId, minimumRole)` helper checks current access for reads. Workspace mutations must call the exported `requireMembershipInTransaction(client, userId, spaceId, minimumRole)` inside their transaction; it holds locks that serialize the mutation with membership removal. The caller identity must come from the authenticated session. Request-supplied actor IDs and role assignments are rejected by strict body schemas. Current membership, not token claims, determines access. Future content idempotency handlers must perform that current membership check before returning any cached mutation result; an idempotency replay must never disclose data to a user whose membership was revoked.

## Migrations, fixtures and tests

`migrations/001_core.up.sql` creates accounts, personal/household spaces, memberships, hashed sessions and invitations. The migration runner records a checksum and applies each numbered SQL migration transactionally under a PostgreSQL advisory lock. Each `.up.sql` has a corresponding `.down.sql` for deliberate manual rollback; no automatic destructive rollback command is provided.

The local-only seed command creates `owner@example.test`, `member@example.test`, `outsider@example.test`, three personal spaces and a household where the first two users are owner/editor. Run `npm run db:seed` for the development database or `NODE_ENV=test npm run db:seed` for the isolated test database. Supply a local-only password without printing it in shell history or logs:

```sh
read -rs -p 'Fixture password: ' SEED_PASSWORD; printf '\n'; export SEED_PASSWORD; npm run db:seed; unset SEED_PASSWORD
```

Run `npm test` with the local databases configured. The test command selects `TEST_DATABASE_URL`, migrates the isolated `creative_cooking_test` database, and refuses any database that is not loopback with that exact name before truncating test tables. It exercises the API against real Postgres and covers registration races, password login, personal workspace creation, owner/editor access, cross-account denial, role and actor-ID substitution, invitation email binding/expiry/replay/concurrent acceptance, membership removal, last-owner protection, session refresh/logout/expiry, CORS origin rejection, rate limiting and body limits. It does not test any content replication engine.
